
### 🔴 P0 Bug: `inject()` → `_input_queue` → `run_loop` 之间有空窗期

**位置**: `engine.py:815-822`

```python
def inject(self, message: str) -> None:
    if not self._running and len(self._active_agents) >= 1:
        self._start_group_loop()
    if self._running:
        self._input_queue.put_nowait(message)
```

问题在于：
1. **`inject()`是同步函数** —— `put_nowait`放进去就走，不做任何中断处理
2. **`run_loop()`正在`broadcast_round()`里面忙** —— agent们都在跑tool_loop，根本没人监听`_input_queue`
3. **只有等到当前broadcast round完成后**，下一轮循环才会回到第784行的`_input_queue.get()`去取新的用户输入

所以场景是这样的：
- Round N: agents在tool_loop里忙着搜索/思考/互发消息（耗时30-90秒）
- 此时用户发了新消息 → `inject()`放进queue ✓
- **但是没有任何东西打断当前的broadcast round** ✗  
- Round N结束后才能读到这条新消息 → delay = entire round duration

### 🟠 P1 Bug: broadcast模式下没有interrupt机制连接用户消息

对比来看：
- **direct_chat模式**(`engine.py:1168-1188`)：有专门的interjection检测循环，agent回复完后等1秒看有没有新用户消息插入上下文
- **broadcast模式**(`run_loop.py:78-121`)：完全没有类似逻辑。一轮开始了就是从头跑到尾

而MailboxHub里的 `interrupt_busy_agents("用户")` (`mailbox.py:431`)虽然实现了设置interrupt event的功能，但它只在MailboxHub.send()中被调用——也就是说只有当某条消息经过mailbox路由时才触达。用户的原始消息走的是 `inject()->_input_queue->run_loop->broadcast_round` ，完全不经过mailbox！

### 🟢 P2 Bug（设计缺陷）：tool_loop的中断检查频率不够高

即使我们解决了上述路由问题，tool_loop中的中断检查点在(`tool_loop.py:205,493,579`)：
1. Iteration开头（LLM调用前）✓
2. Tool批处理执行前 ✓  
3. Tool批处理后 ✓

但如果agent在一个长耗时的单个工具调用中（比如web_fetch一个大网页、exec编译），中间是没有检查点的。

**结论：核心问题是两条路不通。**

```
用户消息 ──→ inject() ──→ _input_queue ──→ run_loop的下一次迭代（太慢！）
                                                                    
应该有的路径：                                                        
用户消息 ──→ inject() ──→ interrupt_busy_agents("用户")

                           → broadcast新一轮                           
```
