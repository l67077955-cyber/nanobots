[Harper]: Kirk 已经给出了完整答案，我来补充一个更直观的解释。

**核心原因：前缀 = system messages，而 system messages 是固定的。**

```
每轮 messages 结构：
┌──────────────────────────────┐
│  System messages (固定)      │ ← 标记了 cache_control，这就是"前缀"
├──────────────────────────────┤
│  "第一轮的问题"        │
│  Assistant: "第一轮的回复"   │
├──────────────────────────────┤
│  "第二轮的问题"        │  ← 这部分增长，但不标记 cache
│  Assistant: "第二轮的回复"   │
└──────────────────────────────┘
```

**为什么不对 history 也加 cache？**

如果每轮把前面所有对话都标记上 cache_control，那前缀确实会逐步增加。但这样做的后果是：

- 第1轮：前缀 = system（~500 tokens）✅ 缓存命中
- 第10轮：前缀 = system + 前9轮对话（~8000 tokens）→ 前缀变了 → 缓存 miss → 重新计算 8000 tokens 的 KV cache

**现在的方式**：system prompt 永远 ~500 tokens，永远命中缓存。对话历史虽然增长但只保留最近 6 轮（`_CONV_KEEP_TURNS=6`），裁剪也只动尾部不动前缀。

一句话：**前缀不变是为了缓存命中，而不是 bug。**

[Kirk]: ## 完整分析：前缀为什么不逐步增加

三层机制共同保证前缀稳定：

### 1. 前缀边界固定 — `_sys_msg_count` 快照

```python
# broadcast.py:685 — agent 启动时拍快照
_sys_msg_count = len(messages)
```

此后 `messages[:_sys_msg_count]` 就是"前缀"，**永不修改**。对话历史从 `_sys_msg_count` 之后开始追加。

### 2. cache_control 只打在前缀上

```python
# litellm_provider.py:213-215 — 只标记 system 消息
sys_indices = [i for i, m in enumerate(messages) if m.get("role") == "system"]
cacheable = set(sys_indices[-sys_quota:])  # 最多 3 个 breakpoint
```

user/assistant 消息**永远不加** `cache_control`。所以 Anthropic 服务端看到的 cache breakpoint 始终落在 system prompt 块内，不会随对话增长而移动。

### 3. 裁剪只动尾部，不动前缀

```python
# tool_pruning.py:220-223 — 只裁剪对话历史
conv_msgs = messages[sys_msg_count:]       # 只取前缀之后的部分
messages[sys_msg_count:] = conv_msgs[-max_conv:]  # 保留最后 6 轮
```

中断处理时甚至**完全不裁剪**（broadcast.py:1044-1047），注释写明："Keeping the full prefix intact guarantees prompt-cache hits."

### 4. 变量分离：稳定 vs 易变

```python
# prompt_builder.py:652-672
stable_tpl_vars  = {agent, members, tools, identity...}   # 放前缀里
volatile_tpl_vars = {datetime, round}                      # 放末尾，不破坏前缀
```

---

**一句话**：前缀 = 系统提示词块，构建后不变；对话历史在下面增长但被定期裁剪到固定窗口，且从不打 cache_control。这样 Anthropic 每次请求都能命中缓存，跳过前缀的重复计算。

[Kirk]: ## 结论

前缀不逐步增加是**刻意设计**，不是 bug。目的是让 Anthropic 服务端 prompt cache 稳定命中，跳过 system prompt 的重复 KV 计算。

## 关键发现

- **`_sys_msg_count` 快照**（broadcast.py:685）：agent 启动时拍下 system messages 数量，此后前缀永不修改
- **cache_control 只打 system**（litellm_provider.py:213-215）：user/assistant 消息永远不加 cache_control，最多 4 个 breakpoint（tools 占 1，system 占 3）
- **裁剪只动尾部**（tool_pruning.py:208-225）：`prune_conversation_tail` 只裁剪对话历史 `messages[sys_msg_count:]`，保留最近 6 轮；中断处理时完全不裁剪
- **变量分离**（prompt_builder.py:652-672）：stable 变量放前缀，volatile 变量（datetime/round）放末尾

## 备注

如果每轮把全部对话标记 cache，前缀会随轮次增长 → 每轮前缀都不同 → 缓存 miss → 反而更差。现在 system prompt 固定不变，永远命中缓存。
