[Harper]: 你说得对。不光是 `break` 加 fallback 的问题，这整个 validation 循环的**前置假设是错的**，修 break 只是止血，不改还会从其他角度崩。

---

**根本逻辑问题：validation retry 的指令自相矛盾**

```
第1轮: LLM → 短文本 (~100字)
系统 → 长度<400，注入警告: "禁止再调用工具，直接输出文字"
第2轮: LLM → 同样的短文本 (~100字)  ← LLM上下文中只有自己的话，没别的可输出
系统 → 还是太短，继续注入警告
第3轮: LLM → 同样的短文本
系统 → retry耗尽 → break → 短文本原封不动发出
```

**矛盾在哪？**

| 系统要求 | 实际能力 |
|---|---|
| "输出结构化总结+具体数据" | 禁止调工具 → 无法召回已丢失的搜索结果 |
| "整合队友发现" | 队友结果是跨 cycle 的，LLM context 可能已被截断 |
| "至少400字" | 上下文中只有自己上一轮的100字，变不出内容 |

LLM 被要求做一件 **不给输入的生产任务**，3次失败后 break，结果和没做 validation 一样。这是一个 **dead-end loop**。

---

**真正的修法不是加 fallback，是改 retry 的数据注入逻辑：**

修 `broadcast.py:1193` 那行 `messages.append(...)` — 在注入警告的同时，把 agent 的工具调用结果（搜索/抓取的内容）**硬拷进 prompt**，而不是让 LLM 凭记忆写：

```python
# 当前做法 (1193-1196:
messages.append({
    "role": "system", 
    "content": "请立即整合所有队友的发现，给出完整、结构化的最终回复..."
})
# ↑ 空口要求，不给数据

# 应该做的:
tool_data = extract_tool_results(messages)  # 从历史消息提取工具输出
fallback_prompt = (
    f"[工具调用结果缓存]\n{tool_data}\n\n"
    "请基于以上数据输出结构化总结（## 关键发现、## 结论），至少400字。"
)
messages.append({"role": "system", "content": fallback_prompt})
```

如果 `extract_tool_results` 也拿不到数据（context 已被截断），**那 validation 本身就形同虚设** — 更上游的问题是 context 管理何时/如何截断 leader 的消息历史，这不是 broadcast.py 能解决的。

所以最小可修范围是：**让 retry prompt 带上数据**，而不是空口要求产生内容。要改吗？
