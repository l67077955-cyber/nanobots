- Step 2: char-budget trimming（从尾部反向填充直到预算用完）

Step 2 的 `seen`/`rebuilt` 去重逻辑是防御性代码——Step 1 已经保证了 head 不在 tail 里。可以简化为：

```python
# Step 2: char-budget trimming
if char_budget > 0:
    head_chars = sum(len(m.get("content", "")) for m in head_msgs)
    available = max(0, char_budget - head_chars)
    head_id_set = {id(m) for m in head_msgs}
    tail = []
    for m in reversed(self.messages):
        if id(m) in head_id_set:
            continue
        c = len(m.get("content", ""))
        if available - c < 0:
            break
        tail.insert(0, m)
        available -= c
    self.messages = head_msgs + tail
```

删掉第二次 `_find_head_indices` 调用和 `seen`/`rebuilt` 去重块。

[Kirk]: ## 结论

**不是长时间运行问题。** 根因是5月17日Kirk模型从`deepseek-v4-pro`切换到`glm-5-turbo`后，synthesis产出变短，频繁触发400字质量阈值被拒重试，每次retry额外消耗~9秒LLM调用。

## 关键发现

**变慢的直接证据（日志时间线）：**
- `10:53:54` leader end_discussion → `10:54:23` synthesis too short (312c < 400) → `10:54:32` retry成功 (784c)
- **end_discussion到最终输出 = 38秒**，其中29秒是synthesis被拒+重试的额外开销
- 进程仅运行31分钟就触发retry，排除长时间运行假设

**根因链条：**
1. `70258ae`（5月17日）Kirk模型 `deepseek-v4-pro` → `z-ai/glm-5-turbo`
2. glm-5-turbo的synthesis产出更短（实测312c、140c），频繁低于`_MIN_SYNTHESIS_LEN=400`
3. 每次被拒 = 额外1次LLM调用；retry exhausted = 3次白费（~27秒）
4. `20774b7`修复了end_discussion后不发synthesis的bug，但让synthesis质量检查更频繁生效

**已提交代码变更（v-stable-20260518 → HEAD）无功能性bug：**
- `broadcast.py` — 修复leader synthesis丢失（FIX）
- `loader.py` — skill compact模式，prompt更短（应该更快）
- `network.py` — 安全加固，无关响应时间

**未提交改动（⚠不要部署）：**
- `context.py` — 删除head_msgs压缩逻辑，会破坏上下文压缩
- `history_settings.py` — 删除7个getter，result_processor fallback到20000默认值

## 备注

**两个修复方向（二选一）：**
1. **降低阈值**：`_MIN_SYNTHESIS_LEN` 400→200，或对简答场景豁免检查
2. **换回模型**：glm-5-turbo的synthesis质量不稳定，切回deepseek-v4-pro可能根本解决问题
