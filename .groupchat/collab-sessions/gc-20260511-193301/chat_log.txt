当上下文变长（特别是接近 100k+ token）时，超时的原因通常分为三类：
1. **TTFT（首字延迟）过高**：Provider 处理长 Prompt 的 Prefill 阶段耗时超过了 API Gateway 的超时设置（通常是 60-120s）。
2. **KV Cache 命中率低**：如果频繁切换任务或 Agent 轮转太快，Provider 无法复用缓存，导致每次都要全量计算。
3. **输出阶段断连**：长上下文导致模型思考变慢，TCP 连接在等待输出时被中间件切断。

**头脑风暴：针对超时的正交优化方案**

*   **方案 A：Prompt 瘦身（不只是压缩）**
    *   **移除冗余工具定义**：如果当前任务不需要 `web_search`，就在这一轮的 System Prompt 中动态剔除该工具的 JSON Schema。
    *   **精简历史消息结构**：只保留最近 5 轮的完整对话，更早的消息仅保留 `Assistant` 的结论，剔除中间的 `Thought` 过程。

*   **方案 B：分段推理（Map-Reduce 思想）**
    *   如果需要处理超长文档，不要一次性塞进上下文。先让一个“阅读 Agent”分段提取关键点，主 Agent 只看提取后的摘要。

*   **方案 C：Provider 策略优化**
    *   **增加超时容忍度**：在 `liteLLM` 调用层将 `timeout` 显式设置为 300s 以上。
    *   **启用流式输出（Streaming）**：即使最终结果不需要流式，开启流式可以保持 TCP 活跃，防止连接因静默被挂起。

Kirk，我建议先检查 `liteLLM` 的超时配置，并尝试在长上下文场景下强制开启流式传输来“保活”连接。

### 修复逻辑
在 `tool_loop` 的每一轮迭代中，根据当前上下文的字符总数（`_ctx_total`）动态计算超时时间：
- **基础超时**：60秒（保证短上下文时的响应速度）。
- **增量补偿**：每 1000 个字符增加 1 秒。
- **公式**：`timeout = 60.0 + (chars / 1000.0)`。
- **优先级**：如果调用方显式传入了 `call_timeout`，则优先使用传入值。

这样当上下文达到 200k 字符时，超时限制会自动放宽到约 260 秒，有效避免了长上下文 Prefill 阶段导致的 408/504 错误。

```python
# nanobot/groupchat/orchestra/tools/tool_loop.py

_current_timeout = call_timeout or (60.0 + (_ctx_total / 1000.0))
logger.debug("tool_loop iter {}: using timeout {:.1f}s for {:,} chars", iteration, _current_timeout, _ctx_total)
```
