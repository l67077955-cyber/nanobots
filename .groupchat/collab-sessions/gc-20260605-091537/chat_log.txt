[Kirk]: ## 结论

为每个代码仓库版本锁定唯一配置仓库 commit，推荐 **`version-lock.json`** 方案——在每个代码仓库根目录放一个声明文件，CI/部署脚本读取后拉取对应配置版本。

## 方案对比

| 方案 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| **A. version-lock.json** ⭐ | 代码仓根目录放JSON声明config commit | 语言无关、可读、可审计、CI易解析 | 需手动或脚本维护 |
| **B. Git Submodule** | `git submodule` 绑定 | Git原生锁定commit | 开发者需recursive clone，CI配置复杂 |
| **C. CI映射表** | pipeline中维护版本→commit映射 | 集中管理 | 散落在CI配置中，不易审计 |

**推荐A**，示例：

```json
{
  "config_repo": {
    "url": "git@github:yourorg/config-repo.git",
    "commit": "30f0acc",
    "tag": "v3.7.1",
    "locked_at": "2026-06-05"
  }
}
```

## 关键发现

- 现有配置仓库仅 1 个有效版本 `30f0acc`（v3.7.1），所有代码版本当前共享同一配置
- 现有版本号体系为日期格式（v-stable-20260517 = "517"），"519" 大概率指 5月19日版本
- 从零设计，无现有绑定机制

## 备注

- 选定方案后可帮你生成批量检查/更新 version-lock.json 的脚本
- "519" 的具体含义（日期/构建号/分支名）确认后可调整 key 命名格式
