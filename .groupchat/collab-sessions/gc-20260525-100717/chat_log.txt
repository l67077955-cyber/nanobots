[Kirk]: 现在逻辑完全清楚了。Harper 之前说的"第192行变量名写错"是错的——实际代码里没有 `target` 变量，两边都是 `sender`。**真正的 bug 更根本：整个释放逻辑被 `if sem:` 守卫，而 "User" 根本没有 semaphore，所以释放块被整体跳过。**

## 结论

**不是"只增不减"，是"只减不增"。** 用户每发一条消息，永久消耗每个 agent 1 个 slot，且永远无法恢复。

## 关键发现

- `allocate_user` (L170): `_available[r] -= 1` — 消耗 **recipient（agent）** 的 slot
- `release_unread` (L188-191): 遍历 `_pending[agent]` 中的 sender，先查 `self._sems.get(sender)`，当 sender="User" 时返回 None → **整个 `if sem:` 块被跳过** → `_available` 从未被修改
- `mark_replied` (L208-211): 同理，`_sems.get("User")` 返回 None → 跳过
- `start_round` (L347-368): 只清队列和历史，**不重置 `_available`**
- Pool 在 `broadcast.py` L315/318 创建，**每 session 一次，不随 round 重建**

**根因**：`allocate_user` 消耗的是 agent 的 slot，但释放路径（`release_unread`/`mark_replied`）试图释放回 sender 的 slot。两条路径不对称，且 "User" 不在 `_sems` 中导致释放被静默跳过。

**效果**：用户发 N 条消息后，每个 agent 的可用 slot 永久减少 N，直到归零后 agent 无法再分配 slot（被阻塞）。

## 备注

Harper 之前定位的"第192行变量名 bug"不准确——实际代码 L190 是 `self._available[sender] = self._available.get(sender, 0) + 1`，变量名一致。真正的问题是这行代码**根本不会被执行到**，因为外层 `if sem:` 已经把 "User" 过滤掉了。修复方向应该是：当 sender="User" 时，把 slot 释放回 recipient（agent_name）而非 sender。

路径现在对称：allocate_user 扣 agent 的 slot → 释放时找不到 sender 的 sem → 还给 agent。
