## Token输入过低的根本原因

看了日志中的 `cache probe` 记录，以及上下文构建逻辑，问题很清晰：

**核心矛盾：Agent的系统提示太长 vs 群聊模式下每个agent独享一份完整system prompt**

从日志看到：
```
cache probe (deepseek/deepseek-v4-flash): 94%
(tools=3ktok, sys10=5ktok, sys11=5ktok, sys12=5ktok)
```

这意味着每次调用传给模型的prompt中，**仅system prompts就有约15KB+**（sys10+sys11+sys12 ≈ 15k tokens），加上tools定义≈3k tokens，总共约18k tokens全是固定的系统指令开销。

而用户的真实输入只有几百token —— 这就是为什么显示"输入的token很少"。实际上并不是真的少，而是**被巨量的system prompt稀释了占比**。

再看几个具体的放大因子：

1. **多份system prompt叠加**：每条消息都携带了完整的角色设定（Kirk的角色描述、Harper的角色描述）、输出效率指南、协作协议、搜索降级策略等多层嵌套的system msg
2. **缓存命中率94%**：说明绝大部分token都是重复的固定开销
3. **群聊广播模式的固有成本**：每个agent看到的context都要加载所有人的profile和历史

这不是bug，这是架构设计的结果 —— 为了保证每个agent都有完整的上下文和行为规范，牺牲了input token的效率。如果要优化，可以考虑把静态system prompt移到server端预填充或缩短各角色的persona长度。

[Kirk]: ## 结论：GLM 5.1 input token 少是正常的

你看到的 GLM 5.1 请求（238-298 input tok）**不是上下文总结，是 web_fetch 网页内容提取**。

### 三条调用路径，模型都是 GLM 5.1

| 路径 | 触发条件 | input 大小 | 代码位置 |
|---|---|---|---|
| **web_fetch 提取** ← 你看到的 | 每次 web_fetch | ~250-300 tok | `chatroom_tools.py:468` |
| 工具输出摘要 | 输出 > 20,000 字符 | 上限 10,000 字符 (~4k tok) | `summarizer.py:55` |
| 历史上下文压缩 | 消息数 ≥ 40 条 | 完整中间段 | `context.py:146` |

### 为什么 input 这么少

web_fetch 提取的 prompt 结构是：
```
[system: 无]
[user: "你是一个网页内容提取助手..." + 网页内容截断到12000字符]
```
没有 system prompt，只有一条 user 消息，所以 input token 只有 200-300。

### 如果你想让上下文总结也用 GLM 5.1 且传入更多 token

当前配置：
- `summarize_max_input_chars`: **10,000**（限制摘要输入）
- `compress_max_summary_tokens`: **600**（限制压缩输出）
- `summarize_threshold`: **20,000**（工具输出超过此值才触发摘要）

这些值在 `~/.nanobot/history_settings.json` 里可以调。但核心问题是：**你看到的低 token 调用根本不是总结，是网页提取**。真正的上下文压缩可能最近根本没触发过（消息数没到 40 条阈值）。
