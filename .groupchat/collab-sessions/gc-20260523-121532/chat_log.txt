[Harper]: 这个问题我来答。核心原因是**工具调度优先级的设计缺陷**——不是逻辑问题，是工程实现问题。

## 根本原因：工具注册顺序 ≠ 最优推理路径

当前系统的工具调用机制是按**注册列表顺序**遍历匹配的，而不是按语义相关性排序。`read_file`/`list_dir` 这类文件系统工具的注册位置在 `memory_palace` **之前**，所以当用户输入中出现"文件""目录""路径"等关键词时，系统优先匹配了文件工具。

## 为什么这是错的

| 维度 | 应该做的 | 实际做的 |
|---|---|---|
| **信息密度** | memory_palace存的是结构化知识（偏好、配置、约定） | 文件系统存的是项目代码和原始数据 |
| **时效性** | 记忆是最新的上下文 | 文件可能是旧版本 |
| **检索成本** | embedding语义搜索 ≈ O(1) | grep/遍历目录 ≈ O(n) |
| **相关性** | "用户喜欢什么艺术家" → 语义匹配记忆 | "用户喜欢什么艺术家" → 没匹配到文件名 → 空结果 |

## 正确的优先级应该是

```
1. memory_palace (search) — 语义检索历史知识
2. memory_palace (recall) — L2按域召回
3. web_search — 实时外部信息
4. read_file/list_dir — 最后兜底
```

## Kirk的回答我看了——他说得对但不够彻底

他说"设计如此"，但真正的问题是：**没有区分「冷存储」和「热知识」的访问路径**。文件系统是冷存储（代码、数据），memory_palace是热知识缓存（偏好、配置、约定）。同一个接口不应该平等对待它们。

如果你想要修复方案：改工具注册顺序，或者加一层意图路由——检测到"找信息/查偏好/回忆"类意图时强制走memory_palace优先。

## 问题诊断

**根因不是工具注册顺序**（那是我的猜测，错了），而是两层问题：

### 层1：prompt_order.json 的结构缺陷

当前顺序：
```
main_prompt → hard_rules → tool_instructions → persona → broadcast_hint 
→ user_context → output_efficiency → skills → leader_prompt 
→ instructions → memory → history → group_context
```

**`memory` 排在第11位**，在 `tool_instructions`、`persona`、`skills`、`instructions` 之后。这意味着模型在处理"先检索记忆"这条指令时，已经先被大量其他上下文稀释了注意力。

### 层2：broadcast.py 中 memory_palace 的注入方式

看 broadcast.py L348-370：`MemoryPalaceTool()` 是在广播初始化时创建的，然后 `registry.register(memory_palace)` —— **它和其他工具在同一层级注册**，没有任何优先级标记。LLM选工具时只看名字匹配度，不看语义重要性。

---

## 优化方案（两处改动）

### 改动A：prompt_order.json — memory提到第2位

```
before: main_prompt → hard_rules → tool_instructions → ...(8个)... → memory
after:  main_prompt → memory → hard_rules → tool_instructions → ...
```

理由：memory段里包含了"先检索记忆"的硬约束，放在前面让模型在接触任何工具指令前先建立这个认知锚点。

### 改动B：tool_instructions — "0.检索记忆"从第5步提到第0步

当前 tool_instructions 里的思维链是：
```
0. 检索记忆 ← ✅ 已经是第0步
1. 明确目标
...
```

这部分本身没问题。问题是它在 prompt_order 里排在太后面了。

---

## Kirk你看这两个改动哪个合理？

1. **只改 prompt_order.json**（memory提前）— 轻量，不影响代码
2. **两个都改** — memory提前 + tool_instructions里强化"检索记忆优先于一切"

我倾向方案1——最小变更，效果可测。如果还不够再加方案2。
