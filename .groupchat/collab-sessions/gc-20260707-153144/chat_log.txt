[Kirk]: ## 结论

法国在计算机发展史上贡献卓著，横跨四个世纪——从17世纪的机械计算器到20世纪的编程语言和网络技术，法国在计算硬件、软件、网络和信息服务领域均有里程碑式成就。

## 关键发现

### 🔧 早期机械计算（17-19世纪）

| 年份 | 里程碑 | 人物/机构 | 意义 |
|------|--------|-----------|------|
| **1642-1644** | **Pascaline（帕斯卡计算器）** | Blaise Pascal | 世界上第一台**批量生产并实际使用**的机械计算器，可进行加减运算。Pascal年仅19岁开始设计，为帮助父亲（税务官）计算而发明。 |
| **1801** | **雅卡尔提花织布机（Jacquard Loom）** | Joseph Marie Jacquard | 利用**打孔卡**控制织花图样，无需更改机械设计即可变更程序。这是**可编程机器**的里程碑，直接启发了Hollerith的制表机（IBM前身），影响了Babbage的分析机。 |
| **1820** | **Arithmometer（四则计算器）** | Charles Xavier Thomas de Colmar | 第一台**商业化成功的**机械计算器，能进行加减乘除四则运算。1851年起量产，**持续生产至1915年**，直到一战仍在使用。 |

### 🏢 计算机产业（20世纪）

| 年份 | 里程碑 | 人物/机构 | 意义 |
|------|--------|-----------|------|
| **1930s** | **Bull公司成立** | Compagnie des Machines Bull | 法国最大的计算机公司，生产大型机和小型机，曾与IBM竞争欧洲市场。1983年收购Micral，后被Zenith收购。 |
| **1973** | **Micral N — 世界首台商用微机** | François Gernelle（设计）/ Truong Trong Thi（R2E公司） | 基于Intel 8008处理器，500MHz，2KB RAM，售价$1900。**比美国MITS Altair 8800早两年**（1975）。后续型号Micral V（1978）是世界首台便携式计算机。 |

## Mod诊断: Eye of Prediction v1.70

**目录结构**：双构建路线的"预言之眼"自动闪避Mod（Isaac重生）
- `root/` — 主构建 (main + danger_detection + dodge_planner)
- `aeb/` — Alternate Eye Build（平行变体，结构镜像）

**核心逻辑链**：每一帧全量扫描房间实体 → 分类危险源（弹幕/近战/激光/炸弹/地板效果）→ 在候选路径上暴力评分 → 选最优闪避方向 → 叠加辅助功能（自动蓄力、隐藏房间提示）

---

### 🔍 算法瓶颈分析（共6项）

#### 🔴 瓶颈1: 每帧全量扫描房间实体 — O(n) 无空间索引
- `danger_detection.lua` 每一帧调用 `Isaac.GetRoomEntities()` 返回房间全部实体
- 对每个实体反复 typecast（`ToProjectile`, `ToNPC`, `ToBomb`, `ToEffect`）冗长无效调用
- 弹幕密集房（如Hush、Delirium）同帧实体数 > 200，每帧全遍历产生严重抖动

**修复方向** → 引入空间哈希网格，分区扫描；entity type 预分类后分组缓存

#### 🔴 瓶颈2: 候选路径暴力评分，每帧 O(candidates×hazards)
- `dodge_planner.lua` 为 `gapCandidateCount=3` 个方向候选计算完整评分
- 每个候选累加：collisionPenalty(12000) + wallPenalty(28) + cornerPenalty(70) + trackingNearPenalty(260) + nearMissReward(190) + …
- **无剪枝**：所有候选全部算完才选出最优

**修复方向** → early termination（得分远劣于当前最优则跳出）；按危险密度预筛选候选

#### 🔴 瓶颈3: `pcall` 滥用 — 每帧千次调用
- 几乎所有游戏API调用（`entity.ToProjectile`, `entity:GetSprite()`, `Input.IsButtonPressed`）都用 pcall 包裹
- 安全是好事，但每帧几百次pcall在 LuaJIT 上每次产生闭包分配 + 异常表查找

**修复方向** → 用类型守卫前置检查（`entity.Type == EntityType.ENTITY_PROJECTILE`）替代 try-catch；仅在IO/远程调用时保留 pcall

#### 🔴 瓶颈4: 每帧大量table GC 压力
- `createHazardPrimitive()` 每帧为每个危险源新建 table + 遍历 fields
- `table.concat({...})` 在主循环中每帧调用创建字符串ID
- LuaJIT GC 在分配量 > 内存2%时触发 full GC cycle，导致帧时间尖峰

**修复方向** → 对象池复用 hazard primitive；原始ID用 `tostring()` 替代 table.concat + 缓存

#### 🔴 瓶颈5: `os.clock()` 多次重复调用
- `nowMs()` 调用 `os.clock()*1000` 在 danger_detection, dodge_planner, main 中每帧各调多次
- debug 模式下频繁记录 ms 精确时间戳

**修复方向** → 在入口处（`MC_POST_UPDATE`）调用一次 `os.clock()`，传引用给子模块

#### 🔴 瓶颈6: `databases.lua` — 线性的 profile 匹配
- NPC profile 匹配用 `npcProfileKey()` 拼合字符串 → `telegraphProfileMatches()` 线性的 token 匹配
- 无 hash lookup，字符串匹配在大表（~40+ profile）上反复进行

**修复方向** → 构建哈希索引表 `type:variant:subtype → profile`，O(1) 查找替代 O(n)

---

### 📊 优化优先级矩阵

| 优先级 | 瓶颈 | 预期收益 | 实现成本 |
|---|---|---|---|
| **P0** | 瓶颈4: GC压力（hazard table allocation） | 🟢 中高 — 消除帧时间尖峰 | 低 — 对象池 | 
| **P0** | 瓶颈6: profile线性匹配 → 哈希索引 | 🟢 中 — 减少字符串操作 | 低 — 建hash表 |
| **P1** | 瓶颈2: 候选评分剪枝 | 🟢 中 — 减少30-40%评分运算 | 中 — 需重写评分循环 |
| **P1** | 瓶颈3: pcall → 类型守卫 | 🟢 中 — 减少闭包分配 | 中 — 逐模块替换 |
| **P2** | 瓶颈1: 空间哈希网格 | 🟡 低中 — 高难度房显著 | 高 — 需引入数据结构 |
| **P3** | 瓶颈5: os.clock()集中化 | 🟡 低 | 低 — 单入口注入 |

服务器上的以撒 mod（`eye_of_prediction_opt_3757138368`）存在 **2个P0级性能瓶颈**、**3个P1级优化点**和 **1个P2级微优化**。核心问题集中在 `danger_detection.lua` 的每帧全量重建和缺乏对象池，Harper 已开始编写 P0-1 对象池修复补丁。

## 关键发现

### 🔴 P0 — 必须修复（每帧热路径）

| # | 问题 | 位置 | 影响 | 修复方向 |
|---|---|---|---|---|
| 1 | **BuildOutput() 每帧全量重建所有 hazard primitive** | `danger_detection.lua:2277` | 即使实体未移动也重建全部 primitive，是 GC 压力根源 | **Dirty flag 机制**：仅当实体位置/状态变化时才重建 |
| 2 | **primitive() 无对象池** | `danger_detection.lua` 多处 | 每帧创建大量临时 table，触发频繁 GC | **对象池复用**：预分配 primitive table 池，帧结束时归还 |

| 5 | **syncDynamicRegistriesFromRoom 与事件回调双重注册** | `danger_detection.lua` | 同一实体被注册两次，产生冗余 Vector clone | 去重检查或统一注册入口 |
