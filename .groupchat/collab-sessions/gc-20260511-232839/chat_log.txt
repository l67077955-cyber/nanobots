如果要实现在构建 prompt 时就自动检索记忆并注入，有两个切入点：

**Option A: 改造 `memory` 组件本身**
在 `_get_component_content` 的 `key=="memory"` 分支里，除了返回 static template，还附加一段动态生成的记忆搜索结果。这需要在 PromptBuilder 层引入对 MemPalace 的直接调用。

**Option B: 新增一个 pre-build hook**
在 `build_agent_prompt()` 的开头增加一步：用当前任务的 query/keywords 去 MemPalace search，然后将结果作为一个新的 system message 注入到 messages list 的前部。

两种方案的权衡：
- Option A改动小，复用现有的 component slot，但不适合放大量动态内容（template var expansion在前）
- Option B更干净，分离关注点，但需要加一个新的 pipeline step

我觉得最优解是在 `build_agent_prompt()` 中加入一个预检索步骤——在所有 component 组装完毕后、但在 volatile timestamp 之前，插入一条带记忆结果的 system message。这样既不影响缓存前缀稳定性，又能确保每条 prompt 都携带相关记忆。

不过等等——这里有个根本性问题：**PromptBuilder.build_agent_prompt() 是同步函数**，而 MemPalace search (`memory_palace(action='search')`) 是通过 tool calling 异步执行的。我们不能直接在 build phase 调用 tool。

**Route 1: MEMORY.md-based（轻量）**
在 memory.md template 中用占位符，然后在 expand_template_vars 阶段替换成从 MEMORY.md/grep 抓取的相关段落。不需要异步调用。

**Route 2: Tool-layer enforcement（重量）**
不改 prompt builder，而是在 agent loop layer（比如 broadcast.py/_run_one）中，在第一次 tool loop iteration 之前强行注入一轮 memory retrieval。类似 leader_hint injection的方式。

**真正可行的路径只有三条，逐一排除法：**

| 方案 | Token成本 | Latency影响 | 确定性 | 侵入度 |
|---|---|---|---|---|
| A) Build-phase grep MEMORY.md关键字匹配 | ≈0 | ≈0ms | ✅高 | low |
| B) First-turn强制tool call检索 | ≥500/turn | +LLM延迟 | ❌取决于model听话程度 | medium |
| C) Hybrid：MEMORY.md定期dump关键memorial片段+A组合 | ≈0 runtime | ≈0ms runtime | ✅最高 | medium |

**我的立场：选C。**

理由链条：
1. **A的问题是覆盖面不够** — 我们之前的架构决定已经把大部分知识移出了MEMORY.md进了mempalace。光靠grep MEMORY.md会漏掉太多。
2. **B的问题是不可控** — 依赖模型在第一轮乖乖调tool_search而不是直接回答。这不是engineering guarantee，是hope-driven development。
3. **C的方案细节：**
   - MEMORY.md底部开辟一块 `## Auto-Injected KB`（≈800 chars上限）
   - 每周/事件驱动的cron job：从mempalace拉top-N高频命中条目反哺进KB区
   - build phase用当前turn的用户query关键词扫KB区的tag header做substring match过滤出相关段落后拼接进去
   - KB区之外的知识走现有workflow（agent自主search）

这就实现了 **零runtime开销 × 全覆盖 × 确定性注入**。
