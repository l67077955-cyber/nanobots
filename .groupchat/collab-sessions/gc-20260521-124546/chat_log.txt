[Kirk]: ## Kirk 超时根因分析

**不是 timeout 太短，是上下文膨胀导致模型推理变慢。**

### 超时事件还原

```
iter 1  12:50:44  exec           13c    cost=0.0250
iter 2  12:50:52  exec x2       849c    cost=0.0105
iter 3  12:51:10  read_file   5,220c    cost=0.0185
iter 4  12:51:27  read_file   8,458c    cost=0.0167
iter 5  12:51:31  read_file   9,739c    cost=0.0141
iter 6  12:51:34  read_file  13,629c    cost=0.0102
iter 7  12:51:35 ──→ 12:53:05  TIMEOUT (90s) ← 模型推理超时
```

### 数据

| 指标 | 值 |
|------|-----|
| call_timeout | 90s（`_gc_defaults`） |
| Kirk max_iterations | 12（leader 角色） |
| 超时发生轮次 | iter 7 |
| iter 1-6 累积 tool result | **~37,908 chars** |
| 估算总输入（含 system prompt + history） | **~45K chars ≈ 11-15K tokens** |
| cost 跳变 | iter 6: $0.010 → 恢复后: $0.058（**5.7 倍**） |

### 根因

**tool_loop 的上下文是累积式的**——每次迭代把上一次的 tool result 追加到 messages 里。Kirk 连续 4 次 `read_file` 大文件（5K-13K chars），到 iter 7 时上下文已膨胀到 ~45K chars。GLM-5-Turbo 处理这个量级的输入时，推理时间超过 90s 硬边界。

**不是模型能力问题，是上下文管理问题。**

### 缓解方向（不加 timeout）

| 方案 | 预期效果 |
|------|----------|
| 限制 `read_file` 单次返回量（如 max 3000 chars） | 直接减少每轮增量 |
| tool_loop 累积 tool result 总量上限（如 20K chars） | 防止无限制膨胀 |
| 对旧 tool result 做摘要压缩 | 保留关键信息，减少 token |
| 减少 leader max_iterations 12→8 | 减少最大累积轮数 |
