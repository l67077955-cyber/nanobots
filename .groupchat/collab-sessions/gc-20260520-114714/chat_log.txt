## 结论

**不是膨胀问题。** 5/18-19 的改动方向是反膨胀，当前 static 前缀约 **11-14K chars**，处于合理区间。唯一真正的膨胀源是 history 线性增长，与这两天的改动无关。

## 关键发现

- **Static 前缀实测 ~11K chars**（含格式开销 ~14K）：main_prompt(1103) + tool_instructions(1730) + output_efficiency(1525) + leader_prompt(1834) + memory(656) + user_context(275) + instructions(493) + group_context(29) + persona(~520) + skills_block(3122)
- **Skills 段占 static 前缀的 29%**（3122/10767）：4个 always-on 技能各截断到 700 chars，总预算 5600 未用满
- **compact 模式实际未启用**：`compact=True` 在代码中从未被调用，但 `MAX_ALWAYS_SKILL_INLINE=700` 的截断机制起到了类似效果（原始总计 8668 chars → 截断后 3122 chars，省 64%）
- **5/18 新增的 5 个组件**（skills_overview, examples, group_nudge, coding_principle, 记忆补充）全部在 dynamic 段（history 之后），不影响 prefix cache
- **History 是唯一膨胀源**：每轮 +2-4 条消息，50 轮时 ~15-25K chars，由 `maybe_compress` 机制控制

## 备注

有一个可优化点：static skills 的 700 chars 截断是暴力截断，而 `build_skills_summary` 有更智能的 compact 模式（description + read_file 指针）。将 static skills 也改用 compact 模式可再省 ~2000 chars（从 3122 → ~1000），但这是微优化，不构成"膨胀问题"。
