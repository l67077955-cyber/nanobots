## 结论
MemoryPalace 有两个机制：**存储**（`_auto_memory.py`，讨论后3次LLM poll写入）和**召回**（`_auto_recall.py`，讨论前3 wing固定召回）。当前召回**完全不用语义搜索**，`user_input` 传了但没用。让 agent 自行生成检索关键词**技术上完全可行，且是当前架构最合理的改进方向**。

## 关键发现

### 当前召回的问题
- `_auto_recall.py` L36：`stack.recall(wing=wing)` → 底层是 `L2.retrieve()`，按元数据过滤+插入顺序返回，**零语义相关性**
- `user_input` 只拼到 header 里给 agent 看（L65-66），`_recall_wing()` 完全不使用它
- 结果：**每轮群聊注入的记忆完全相同**，不管用户问什么

### 让 agent 自行生成检索关键词的可行性

**方案A：在 `_auto_recall.py` 里加一步 LLM 生成关键词（推荐）**
```
user_input → LLM提取3-5个检索关键词 → L3.search(keywords, wing=wing) → 注入
```
- 优点：关键词质量高，LLM 理解用户意图后能生成中英文+同义词
- 缺点：多一次 LLM 调用（~2s），但 recall 在 broadcast 前执行，延迟可接受
- 实现：复用现有的 `summarize_model`（glm-5.1），temperature=0.3

**方案B：直接用 user_input 做语义搜索（最简）**
```
user_input → L3.search(user_input, wing=wing) → 注入
```
- 优点：零额外成本，改一行代码
- 缺点：用户输入可能很短（如"发我"），语义搜索效果差

**方案C：混合（A+B）**
```
user_input → LLM生成关键词 + user_input原文 → 分别search → 去重合并
```
- 最强但最复杂，当前阶段没必要

### 我的建议
**方案A**。原因：
1. 用户输入经常很短/模糊（"发我"/"快一点"/"看看"），直接做语义搜索召回率低
2. LLM 生成关键词可以覆盖中英文+同义词+缩写，这正是 ChromaDB 语义搜索的弱点
3. 额外 2s 延迟在 broadcast 前完全可接受
4. 与现有的 4区块 SOP（`memory-search-sop`）理念一致——agent 手动搜索时也是先想关键词再搜

## 备注
- `L3.search()` 已支持 `wing` 过滤+`n_results` 控制，基础设施完备
- 唯一需要注意：LLM 生成关键词的 prompt 要明确要求"中英文+同义词+缩写"，否则可能只生成中文关键词，漏掉英文内容

[Harper]: 对，你说的没错。让我重新审视一下这两个文件的本质差异。

`_auto_recall.py`（68行）和 `_auto_memory.py`（275行）虽然都和 mempalace 相关，但：

- **recall**：讨论前执行，同步调用 ChromaDB，零 LLM 开销
- **store**：讨论后执行，3次异步 LLM poll + ChromaDB 写入

它们唯一的共同点是"都操作 mempalace"，除此之外没有任何共享代码、没有数据依赖、触发时机完全不同、一个是同步一个是异步。

强行合并反而会让文件内聚性变差——一个函数做 recall（同步+搜索），另一个做 store（异步+LLM+写入），放在一起只是物理上的"同一个目录"，逻辑上是两个独立模块。

而且 `run_loop.py` 的 import 已经很清楚：
```python
from nanobot.groupchat.orchestra._auto_recall import auto_recall_memories
from nanobot.groupchat.orchestra._auto_memory import auto_store_memories
```

**召回 vs 存储，以及"agent自行生成检索关键词"**

## 两个机制

| | 存储 (`_auto_memory.py`) | 召回 (`_auto_recall.py`) |
|---|---|---|
| 时机 | 讨论结束后 | 讨论开始前 |
| 方式 | LLM提取→ChromaDB写入 | ChromaDB查询→注入系统消息 |
| 引擎 | `tool_add_drawer` (sha256去重) | `L3.search()` (语义搜索) |

## "agent自行生成检索关键词"

**技术上可行，但当前不需要。**

理由：
1. **ChromaDB是语义搜索**（embedding cosine sim），不是关键词匹配。自然语言 query="看看mempalace的轮询逻辑" → embedding空间里自动匹配相关概念，不需要人工拆关键词
2. **加一步LLM生成关键词**：user_input → LLM提炼3-5个关键词 → 分别search → merge结果。好处是精度略高，代价是+2-3s延迟+一次LLM调用
3. **什么时候需要**：当 user_input 非常模糊（比如只说"查一下"）或者用户习惯用代词指代时，LLM扩写有帮助。但目前场景下 user_input 本身已经是自然语言问题，直接喂给语义搜索就够了

**结论：可以加但没必要。Kirk的实现（直接用user_input做query）是最优解。**
