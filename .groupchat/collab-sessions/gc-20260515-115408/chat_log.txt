[Harper]: 好，Kirk 的分析很扎实。我来补充几个关键判断：

## 我的评估 — 哪些真值得抄，哪些是坑

### ✅ 值得落地的（改动小/收益高）

**1. 工具结果预摘要（Phase 1）**
- hermes 把 >200 chars 的工具结果替换为 1 行描述
- nanobot 目前是整段保留，压缩时才一起扔给 LLM
- **收益**：省 HistoryContext 存储空间，省压缩 LLM 调用次数
- **改动**：在 `result_processor.py` 管线末端加一步轻量摘要（正则/规则即可，不需要 LLM）

**2. 结构化压缩模板**
- hermes 的 Goal/Progress/Decisions/Files/Next Steps 模板
- nanobot 目前是自由文本摘要，信息密度低
- **收益**：压缩后的摘要可检索、可追溯
- **改动**：改 `context.py` 的 `maybe_compress` 中调用 LLM 的 prompt

**3. Context files 安全扫描**
- hermes 检测 prompt injection、零宽字符、超长行
- nanobot 没有任何安全检查
- **收益**：防恶意 AGENTS.md 注入
- **改动**：加一个 `_sanitize_context_content()` 函数

### ❌ 不推荐的（坑）

**1. 滚动窗口缓存（system_and_3）**
Kirk 说得对——多 agent 群聊场景下，agent 消息不可预测，尾部缓存大概率 miss。而且每轮 cache prefix 变化，system prompt 的缓存也会受影响。**nanobot 的 system-only 策略更适合群聊。**

**2. 双层压缩**
Gateway 层的 85% 阈值在 nanobot 场景下意义不大——nanobot 的 HistoryContext 已经有 30 条/50k chars 的硬上限，再加一层 Gateway 是过度工程。

**3. 迭代重压缩**
理论上好，但实际上需要维护压缩状态（上次摘要内容），复杂度上升明显。nanobot 的压缩触发频率不高（≥21 条才触发），重新生成的成本可以接受。

### 🎯 建议落地顺序

1. **工具结果预摘要** — 半天，纯规则，不改架构
2. **结构化压缩模板** — 1天，改 prompt 即可
3. **Context files 安全扫描** — 半天，独立函数

[Kirk]: ## 结论

hermes-agent 的上下文架构有 6 个可借鉴设计，但**滚动窗口缓存不适合 nanobot**（多 agent 群聊场景下尾部缓存频繁 miss，收益为负）。真正值得落地的 TOP 3：

| 优先级 | 改进点 | 改动位置 | 收益 |
|--------|--------|----------|------|
| 1 | 结构化压缩摘要模板 | `context.py:maybe_compress` | agent 恢复时快速定位状态 |
| 2 | 迭代重压缩 | `context.py:maybe_compress` | 防信息逐轮退化 |
| 3 | 工具结果预摘要 | `result_processor.py` | 省压缩 LLM 预算，提高摘要质量 |

## 关键发现

**缓存策略对比：**

| | hermes-agent | nanobot |
|---|---|---|
| 策略 | `system_and_3` | system-only |
| 缓存点 | system + 最后3条非system | 仅 system |
| 多 agent 场景命中率 | 尾部频繁 miss | system 100% 命中 |
| 前缀稳定性 | ❌ 压缩破坏缓存（已知缺陷） | ✅ `_sys_msg_count` 快照保证 |

**压缩算法对比：**

| | hermes-agent | nanobot |
|---|---|---|
| 阶段数 | 4（预摘要→边界对齐→结构化→清理） | 1（head-middle-tail） |
| 模板 | Goal/Progress/Decisions/Files/Next Steps | 自由文本 |
| 重压缩 | 迭代更新 | 每次从头生成 |
| 层数 | 双层（Gateway 85% + Agent 50%） | 单层（70%） |

**不适合借鉴的：**
- 滚动窗口缓存 — 多 agent 消息不可预测，尾部缓存命中率接近 0
- hermes 的压缩破坏 KV cache 前缀是已知缺陷，nanobot 的 `_sys_msg_count` 快照设计更优

- 双层压缩和可插拔引擎是远期方向，当前单层够用
- 上下文文件渐进发现和安全扫描属于锦上添花
