## 1. ❌ `Pipeline.run()` 接口太泛化——忽略触发时机异构

Kirk说"4个Stage严格线性顺序"，但实际**触发时机完全不同**：

| Stage | 触发时机 | 消息上下文 |
|-------|---------|-----------|
| S1 截断 | 每次工具返回后（增量） | 单条 tool message |
| S2 AI摘要 | S1后，超8K字符 | 单条 tool content |
| S3 修剪 | `add_message` 调用时 | 完整 messages list |
| S4 压缩 | 消息数超 `keep_turns*3` | 完整 messages list |

**问题**：统一的 `run(messages)` 迫使 S1/S2 每次都要遍历整个 messages list 找哪个是新加的。现有代码在 `result_processor.py` 里是增量处理的（只处理刚返回的那条工具结果），重构后反而退化。

**修正**：Pipeline 暴露两种入口：

```python
class CompressionPipeline:
    async def process_tool_result(self, tool_msg: dict) -> dict:
        """S1 + S2：增量处理单条工具结果"""
        ...
    
    async def maybe_compress(self, messages: list[dict]) -> list[dict]:
        """S3 + S4：全局压缩（add_message / 溢出时触发）"""
        ...
```

## 2. ❌ 无错误恢复策略

当前代码的容错机制：任一阶段失败，静默返回原始内容（不中断会话）。Kirk的Pipeline用 `for stage in self.stages: messages = await stage.process(messages)`——如果某个stage抛异常，**整条管线中断**，返回空或半处理结果。

**修正**：每个Stage加`graceful_fallback=True`，默认捕获异常回退：

```python
async def run(self, messages):
    for stage in self.stages:
        try:
            if stage.should_run(messages):
                messages = await stage.process(messages)
        except Exception:
            logger.warning(f"[Pipeline] Stage {stage.name} failed, using fallback")
            # messages 保持原样，不中断
    return messages
```

## 3. ❌ Phase 0 测试覆盖率不够

> "各写1个集成测试" —— 太模糊

每Stage最低需要这些边界测试才算行为快照：

| Stage | 必要测试场景 |

| S1 | 超大结果(>8K), 空结果, 刚好在阈值边界的 |

| S4 | 丢弃<5条不调LLM, 丢弃≥5条调LLM, 摘要分割符替换去重 |
