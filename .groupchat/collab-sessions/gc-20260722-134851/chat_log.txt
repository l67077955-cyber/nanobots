## Bug 分析与修复

### 🐛 Bug 1（致命）— 第二只鸟之后无法发射
**行：** `settleNextBird()` (191-197)、`updateUI()` (278-281)、`gameLoop()` (302-304)

**症状：** 第一只鸟飞完后，玩家能看到下一只在弹弓上，但点击拖不动。

**根因链路：**

1. `mouseup`/`touchend` 设置 `birdLocked=true`（行224/258）
2. `settleNextBird()` 把刚着陆的鸟设为 `active=false`（行194），设 `birdLocked=false`（行196）
3. **但是** `settleNextBird()` **从未被调用过！**
4. 唯一可能触发的地方是 `gameLoop()` 中的这段（行302-304）：

```js
// Auto-settle landed birds
for(let b of birds){
  if(b.launched&&b.active&&Math.abs(b.vx)<0.3&&Math.abs(b.vy)<0.3&&b.y>=GROUND-b.r-2){b.active=false;birdLocked=false;}
}
```

这里虽然做了类似的事，但它是在遍历中直接修改数组元素属性。问题是：这只处理了「落地」的情况，但如果小鸟飞到右边撞墙停下但没有落到地面高度（比如卡在半空中或者刚好在地面附近震荡），这个条件就不满足，`birdLocked`永远不会变成 `false`。

更关键的漏洞：即使这行生效解除了锁定，下一次 `mousedown` 的事件处理器开头就有：

```js
if(birdLocked||birdInFlight())return;
```

而 `birdInFlight()`（行188-189）的条件非常宽松——只要任何一只鸟的速度绝对值 >0.5 OR y坐标低于阈值就会阻止交互。这意味着上一只鸟还没完全停止的时候就不能抓新的。

**修复方案：**

```javascript
function settleNextBird(){
  for(let b of birds){
    if(b.launched&&b.active){b.active=false;break;}
  }
  birdLocked=false;
}

// In game loop, replace the inline logic with proper settling detection:
// After collision handling and removal loops, add:
if(!birdInFlight() && !getActiveBird() && birdLocked){
  settleNextBird();
}
```

并且将 mouseup/touchend 里的 `birdLocked=true; activeBird=null;` 改为仅在确实发射时才锁。

### 🐛 Bug 2（高）— pig vs pig、block vs block 碰撞无反应
**行：** `checkCollision()` (86-103)

函数签名接受两个对象，但在计算距离时用了 `.r || 18` ——对于 Pig(Pig类有 r=22)，它用的是后备值18而不是实际的22。而且pig之间的碰撞根本没有伤害逻辑。

另外在 `handleCollisions()` (128-143)中，只有特定组合才有伤害效果：
- Block+Bird ✓
- Pig+Bird ✓  
- Block+Block ✓
- **Pig+Pig ✗**
- **Pig+Block ✗**

所以猪叠在一起不会受伤也不会推开彼此。

### 🐛 Bug 3（高）— touch事件的 hit area比鼠标大太多
**行：** mousedown (205) vs touchstart (236)

鼠标：hit radius = **40**
触屏：hit radius = **50**

这不是对称设计而是不一致。更大的半径意味着手指更容易误触激活弹弓拖动。

### 🐛 Bug 4（中）— slingshot视觉跟随不对
**行：** `drawSlingshot()` (262-268)

皮筋画线是从固定锚点到小鸟当前位置。但当用户在屏幕上滑动时，实际上更新的是全局变量 `dragStartX/Y` ，并没有真正移动小鸟的位置。因此皮筋的一端固定在初始位置不变，另一端跟着光标走的效果是对的——但这只是视觉效果没问题的情况下。

真正的bug在于松开后的力量计算使用了最后记录的 dragStartX/Y，而这个值是相对于canvas坐标系转换过的client坐标，并不是基于小鸟位置的偏移向量。这在大多数情况下近似正确但不精确。

---

### 🐛 Bug 5（中）— level大于3时的关卡构建崩溃风险
**行：** `buildLevel(n)` (147-178)

第151行的条件是：
```js
if(n>=3)birds.push(new Bird(240,GROUND-20));
```

而当 n=4时，因为没有对应的关卡布局分支（只有n===1、n===2、else对应n≥3），它会落入else分支生成第三关的地图。但此时会有4个关卡的内容混搭感不明显的问题。

更重要的是 `nextLevel()` (327)：
```js
function nextLevel(){level++;if(level>3)level=1;buildLevel(level);}
```

这里的限制是正确的——最大回到第1关。但是如果有人手动在控制台输入 `buildLevel(999)` ，由于没有防御措施会导致大量push进数组造成性能问题甚至OOM。

### 🐛 Bug 6（中）— allBirdsDone判定过于苛刻容易死锁
**行：** `allBirdsDone()` (146)

```js
return birds.every(b=>!b.active||(b.launched&&Math.abs(b.vx)<0.3&&Math.abs(b.vy)<0.3&&b.y>=GROUND-b.r-2));
```

如果一个鸟被标记为 launched=true && active=true，但因为某些原因它的 vy != ±小范围波动内或者 y >= GROUND - r -2不成立（比如它在斜坡上停下来），那么它就永远不会被认为是done的状态。结合Bug1的分析，这会永久阻塞界面。

### 🐛 Bug 7（低）— score溢出无上限
分数累加没有任何上限检查。理论上玩得够久可以达到JS安全整数以上出现精度损失。

### 🐛 Bug 8（低）— CSS按钮重叠在小屏设备上
CSS media query (`@media(max-width:640px)`)只设置了canvas自适应宽度和高度的auto比例缩放，但是没有调整UI区域的flex-wrap或间距。"重来""下一关"两个按钮可能在窄屏手机上挤在一行超出容器宽度。
