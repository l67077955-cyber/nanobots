## 结论

**不稳定。** 动态编排生成的历史在后续调用中**不保证一致**，有三个确定性破坏点。

## 关键发现

### 确定性链路分析

| 环节 | 是否稳定 | 原因 |
|------|---------|------|
| `age_tool_log()` | ✅ 稳定 | 纯正则替换，同输入同输出 |
| `strip_tool_log()` | ✅ 稳定 | 纯正则删除 |
| `agent_ranks` 计算 | ✅ 稳定 | 从静态配置读取，`_agent_ranks_cache` 缓存 |
| `history_settings` 值 | ✅ 稳定 | 从 JSON 文件读取，进程内不变 |
| **`history_to_messages` 尾部截断** | ❌ **不稳定** | 见下 |
| **`prune_conversation_tail_with_summary`** | ❌ **不稳定** | 见下 |
| **`maybe_compress`** | ❌ **不稳定** | 见下 |

### 三个确定性破坏点

**1. 滑动窗口截断（`message_converter.py:136-148`）**

```python
for m in reversed(msgs_full):
    if budget - c < 0:
        break  # ← 截断点随 history 增长而移动
    tail.insert(0, m)
    budget -= c
```

同一条消息在 round 3 可能被包含，round 10 被排除。**截断边界是 history 长度的函数，不是消息内容的函数**。这意味着 agent 看到的上下文窗口在不断滑动。

**2. AI 摘要压缩（`tool_pruning.py:prune_conversation_tail_with_summary`）**

```python
response = await provider.chat_with_retry(
    messages=[{"role": "user", "content": prompt}],
    model=model, max_tokens=600,
)
```

当 dropped ≥ 5 条时调用 LLM 生成摘要。**LLM 输出不确定**——同一批被丢弃的消息，两次调用产生不同摘要。这个摘要被注入到 system 消息末尾（`messages[last_sys_idx]["content"] += summary_block`），直接改变后续所有 agent 看到的 system prompt。

**3. `maybe_compress`（`context.py:156`）**

单 agent 模式下每次回复后调用，用 AI 压缩中间区域。broadcast 模式不直接调用，但 `prune_conversation_tail_with_summary` 在 broadcast 中每轮都执行（`broadcast.py:1354`），效果等价。

### 传导效应

```
Round 1: history=[A,B,C] → agent看到 [A,B,C]
Round 5: history=[A,B,C,D,E,F,G,H] → agent看到 [A,摘要,G,H]  ← C,D,E,F 被AI摘要替换
Round 6: history=[A,B,C,D,E,F,G,H,I] → agent看到 [A,摘要',H,I]  ← 摘要内容不同，G也被挤出
```

**同一个 agent 在不同 round 看到的"同一批早期消息"的表示不同**——要么被截断、要么被不同摘要替换。

### 唯一稳定的部分

- system prompt 模板本身（不含动态注入的摘要）
- agent 自身配置（rank、tools、persona）
- `age_tool_log` 对单条消息的处理（给定相同输入）

## 备注

- 这不是 bug，是**有意的权衡**——用确定性换取上下文窗口利用率。如果要求绝对稳定，需要固定窗口大小+禁止 AI 压缩，代价是上下文利用率大幅下降。
- 如果要提升稳定性而不完全禁止压缩：可以用**确定性摘要**（如提取关键句、保留结构化字段）替代 LLM 摘要，或者对同一批消息缓存摘要结果。
