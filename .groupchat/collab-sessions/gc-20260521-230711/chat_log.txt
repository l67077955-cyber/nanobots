## 问题诊断：LLM 输出重复循环

### 根因分析

这是 **注意力坍缩到局部 n-gram 的因果LM固有缺陷**，不是单一原因。触发条件通常是：

1. **上下文过长 → 注意力稀释**：tool_loop积累了大量tool result回填，模型丢失了对全局语义的跟踪，退化为"盯着刚生成的最后一个token预测下一个"，形成自激循环。
2. **工具调用触发全量回填**：read_file/exec返回大量文本，回填到messages后的position embedding把模型"淹"了。你的kirk-timeout-analysis已记录这个机制。
3. **缺乏输出层的反重复保护**：现有tool_loop只有工具调用层面的dedup（同参数同结果），没有文本输出层面的detect-and-break。

### 检测策略（三层防御）

**第一层：生成时实时检测（最优）**

在 tool_loop 每次 LLM 返回文本后，LLM输出解析前插入检查：

```
def has_repetition_loop(text: str, threshold: float = 0.85, window: int = 3) -> bool:
    """
    检查文本是否陷入重复循环。
    - n-gram重叠检测：滑动窗口内相邻n-gram的Jaccard相似度
    - 或更简单的：检测同一个句子/N-gram连续出现次数
    """
    sentences = [s.strip() for s in re.split(r'[。！？.!?]', text) if s.strip()]
    if len(sentences) < window * 2:
        return False
    
    # 检查最后 window 个句子是否有大量重复
    last = sentences[-window:]
    prev = sentences[-window*2:-window]
    # 计算重复比率
    overlap = sum(1 for s in last if s in prev) / len(last)
    return overlap > threshold
```

更轻量的方法：**检测连续重复子串**（针对你截图中的同句重复）：

```python
def has_contiguous_repeat(text: str, min_repeat: int = 3) -> bool:
    """检测同一子句连续出现≥min_repeat次"""
    from collections import Counter
    # 按换行或句号分割
    segments = re.split(r'[\n。]', text)
    for i in range(len(segments) - min_repeat + 1):
        if all(s.strip() == segments[i].strip() for s in segments[i:i+min_repeat]):
            return True
    return False
```

**第二层：跨轮次检测（次优，但不延迟推理）**

比较当前完整输出与上一轮LLM输出的最后N个字符的余弦/编辑距离。如果高度相似→命中。

已在 context_pruning_ai_summary 记忆中有类似去重逻辑（反重复注入去重）。

**第三层：工具调用模式异常检测**

如果模型正在产生重复输出，工具调用也会显式异常——连续调用同一个工具、或者连续几轮工具调用结果完全一样。tool_loop已有_sequential_identical_count逻辑，可以扩展。

### 处理策略（触发后怎么救）

**方案A：强制重置上下文（推荐，已有基础设施）**

检测到重复后，注入一条system-level干预消息：

```
[System Note: 检测到输出重复循环。已裁剪最近的 {N} 条消息。请基于最新的目标和关键进展继续。禁用在回复中重复之前的句子。]
```

配合 `prune_conversation_tail_with_summary()`（已有），保留摘要裁剪尾部，然后强制重新推理——这是最有效的，因为根本原因是上下文淹没了模型。

**方案B：中断循环 + 降低temperature**

在tool_loop中对重复检测命中后，下一个iteration用 `temperature=0.7`、`frequency_penalty=0.3`（增加对已出现token的惩罚）。当前系统支持 `sampling_params` 传递。

**方案C：直接break + 错误上报（最保守）**

一旦检测到连续重复输出≥N次，直接break tool_loop，将"output_repetition"作为error_reason返回broadcast层。broadcast已有error recovery（`_consecutive_error_count` 最多3次），可以复用。

### 总结：最小改动路径

| 层 | 改动点 | 复杂度 |
|---|---|---|
| 输出检测 | tool_loop.py `_run_llm_and_tools()` 返回后加 `has_contiguous_repeat()` | 低(10行) |
| 跨轮比较 | engine.py `_run_loop()` 存 `last_output` 做编辑距离 | 低(5行) |
| 干预注入 | tool_loop.py 检测命中后注入system干预 + 裁剪上下文的调用 | 中(20行) |
| temperature | 命中后下一个iteration改为 `sampling_params.temperature=0.7` | 低(3行) |

**最直接的答案**：你的截图中模型重复"我还需要检查..."那行，是因为上下文在之前的iterations累积了太多tool result，模型失去了对"我已经说过了什么"的跟踪。**上下文裁剪摘要（已有基础设施）+ 输出层n-gram重复检测（需要10行代码）** 即可消除这类问题。

## 关于重复消息问题的分析

你贴的那段消息——同一句话重复了6+次——是典型的 **LLM 退化循环（degenerate repetition）**，不是代码 bug。现有防护机制和缺口：

### 现有防护
1. **broadcast.py:1361-1375** — `_anti_repeat_tag`：在 agent 收到队友消息后注入 system 提醒"你已经发表过上述观点"。但这只在 **跨 cycle 收到新消息时** 触发，不覆盖同一 cycle 内 tool_loop 的输出
2. **provider 层** — `frequency_penalty: 0.1`, `presence_penalty: 0.05`, `repetition_penalty: 1.15`（httpx_provider.py:68-70）。值偏低，对句级重复几乎无效
3. **tool_call 去重** — tool_loop.py:439-460 检测同 batch 内重复工具调用，标记 `duplicate: True`。但这只管工具调用，不管文本内容

### 缺口（为什么没拦住）

| 缺口 | 说明 |
|------|------|
| **无文本内容重复检测** | tool_loop 对 LLM 返回的 `content` 字段没有任何重复度检查。如果模型不调工具、只输出文本，重复内容直接通过 |
| **penalty 值太低** | `frequency_penalty: 0.1` 对 token 级微调，句级重复（几十个 token 的完整句子）几乎无感 |
| **anti_repeat 只在跨 cycle 触发** | 重复发生在单次 LLM 输出内部，broadcast 层的注入根本没机会介入 |
| **无 max_iterations 内的退化检测** | tool_loop 有 `max_iterations` 限制总轮数，但没有"连续 N 次输出相似度 > 阈值则提前终止"的逻辑 |

### 建议方案（按投入/收益排序）

**方案1：tool_loop 内加文本重复检测（推荐，最直接）**

在 tool_loop.py 每次 LLM 返回后、追加到 history 前，检查 `response.content` 与上一次迭代的 content 的相似度：

```python
# tool_loop.py, 在 result.latency += latency 之后
if response.content and _prev_content:
    # 快速检查：连续相同或编辑距离极低
    if _fuzzy_repeat(response.content, _prev_content, threshold=0.8):
        logger.warning("tool_loop iter {}: degenerate repetition detected, breaking", iteration)
        break
_prev_content = response.content
```

`_fuzzy_repeat` 可以用简单的：去空白后相等 / Jaccard on n-grams / 或者直接 `difflib.SequenceMatcher.ratio() > 0.8`。不需要复杂模型，因为退化重复通常是**近乎逐字复制**。

**方案2：提高 provider 层 penalty**

把 `frequency_penalty` 从 0.1 提到 0.3-0.5，`presence_penalty` 从 0.05 提到 0.2。成本低但效果不确定——对句级重复的抑制力因模型而异。

**方案3：post-hoc 截断**

在 tool_loop 返回 content 后、写入 history 前，检测并截断重复尾部。比如发现最后 N 个句子与前 M 个句子高度重叠，只保留不重复的部分。这比方案1复杂且治标不治本（模型下一轮可能继续重复）。

**我的判断**：方案1是正解。退化重复几乎总是连续迭代间的高相似度，一次 `SequenceMatcher` 检查成本可忽略（content 通常 < 几千字符），且能直接终止浪费的迭代。方案2可以作为辅助但不应依赖。

```
   presence_penalty: 0.05 → 0.25
   成本: 改2个数字，零推理开销，所有模型生效
   
Layer 2 (迭代级→降低影响): tool_loop跨迭代相似度检测
   实现你说的 _fuzzy_repeat()，但不是break，而是:
   a) 注入system note + 裁剪上下文（调用prune_conversation_tail_with_summary）
   b) 下一个iteration override sampling → temperature=0.9, frequency_penalty=0.8
   必须在break前做修复，否则break后下一轮还是废的

Layer 3 (最外圈→止损): 连续检测到重复≥2次 → 硬break + error_reason="degenerate_repetition"
   让broadcast层接管，注入退避

```

### 关键争议点：`SequenceMatcher.ratio() > 0.8`

你这个阈值是拍脑门的。退化重复有两种模式：

| 模式 | 特征 | 最佳检测器 |
|------|------|-----------|
| **逐字重复** | 同句连续出现N次 | 子串精确匹配（O(n)） |
| **语义徘徊** | 围绕同一观点用不同措辞反复说 | SequenceMatcher（O(n²)） |

你遇到截图里那种"我还需要检查..."连刷6次的，是**逐字重复模式**，用 `SequenceMatcher.ratio()` 浪费CPU——一个简单的 `has_contiguous_repeat()`（按句号split后精确比较相邻段）O(n)就够，0.98阈值都行。

`SequenceMatcher.ratio() > 0.8` 是给**语义徘徊模式**用的，需要更大的计算量和更低的阈值。

### 总结修正

| 你的方案 | 我的纠正 |
|----------|---------|
| 方案1(重复检测)放首位 | 应放第二层，第一层是提高penalty |
| 方案2(提高penalty)辅助 | 这是第一道防线，优先级最高 |
| penalty提到多少 | 0.1→**0.4**，不是模糊的"0.3-0.5" |
| 检测到重复后break | **先修复上下文+调采样再break**，否则break无效 |
| SequenceMatcher一刀切 | 分两种模式用不同检测器 |

所以正确的修复优先级：**改两个数字 > 加重复检测 > 加修复逻辑**。不是反过来。

[Kirk]: ## 结论

**`total_latency` 不包含工具执行时间。** 它只累积每次 LLM 调用的推理+网络耗时。工具执行时间单独记录在 `tool_calls_detail[].duration`，不回流到 `result.latency`。

**重复消息是 LLM 退化循环**，根因是 tool_loop 迭代累积大量 tool result → 上下文膨胀 → 模型注意力坍缩到局部 n-gram → 自激重复。

## 关键发现

- **tool_loop.py:261/343/353** — `t0` 在 LLM 调用前，`latency = _time.time() - t0` 在返回后，只覆盖模型推理
- **tool_loop.py:503-510** — 工具执行有独立计时 `tc_duration`，不汇总到 `result.latency`
- **broadcast.py:1361-1375** — `_anti_repeat_tag` 只在跨 cycle 触发，不覆盖同一 cycle 内 tool_loop 输出
- **provider 层 penalty 值偏低**（frequency:0.1, presence:0.05），对句级重复几乎无效

## 推荐修复方案

| 层 | 改动 | 复杂度 |
|---|---|---|
| **检测** | tool_loop 内加 `has_contiguous_repeat()` — 检测同一子句连续出现≥3次 | ~10行 |
| **处理** | 命中后 break + 注入 system 干预 + 调用 `prune_conversation_tail_with_summary()` 裁剪尾部 | ~20行 |
| **辅助** | 提高 `frequency_penalty` 到 0.3-0.5 | 改1个数字 |

核心思路：**检测用 `has_contiguous_repeat()`（O(n)，精准匹配连续重复），处理用已有的上下文裁剪基础设施**，最小改动路径约30行代码。
