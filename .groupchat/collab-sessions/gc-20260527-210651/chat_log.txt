## 结论
MemoryPalace 的默认轮询逻辑**基本正确**，有一个值得注意的设计问题和两个小瑕疵。

## 关键发现

**1. `_auto_memory.py` — 3次LLM轮询（讨论结束后触发）**
- 顺序执行：Poll1(技术上下文→wing_code) → Poll2(用户偏好→wing_user) → Poll3(固定信息→wing_agent)
- 每次独立 try/except，一个失败不影响后续
- **跳过逻辑正确**：`len(content) > 50 and "无" not in content1[:20]`，避免存垃圾
- **room 命名用日期+topic slug**：`round-{timestamp}-{topic_slug}`，不会重复覆盖
- **模型用 summarize_model**（glm-5.1），temperature=0.3，合理

**2. `mailbox.py` — wait() 的 5秒轮询间隔**
- `_POLL_INTERVAL = 5.0`，用 `asyncio.wait_for(q.get(), timeout=poll)` 实现非阻塞轮询
- **关键设计**：每5秒检查一次 `_get_busy_expected_repliers()`，如果有队友还在处理你的消息，自动延长 deadline（最多12次×5s=60s额外等待）
- 这防止了"你发了消息给队友，但队友还在跑工具，你先超时退出"的竞态问题

**3. 问题点**

| 问题 | 严重度 | 说明 |
|------|--------|------|
| 3次poll串行，延迟叠加 | 低 | 每次LLM调用约2-5s，3次串行=6-15s。可并行但收益不大，且串行更稳定 |
| `"无" not in content1[:20]` 判断脆弱 | 低 | 如果LLM先写了一段正常内容再写"无"，前20字不含"无"就会存入。但实际很少触发 |
| `_MAX_EXTENSIONS=12` 硬编码 | 极低 | 60s额外等待对大多数场景够用，极端情况（大模型推理慢）可能不够 |

## MemPalace 默认轮询逻辑分析

### 1. `_auto_recall.py` — 讨论前自动检索 ✅

**触发时机**：`run_loop.py:L132-138`，每轮广播前执行

```python
recalled = await auto_recall_memories(user_input=user_input)
if recalled:
    engine._add_message("系统", recalled)
```

**内部逻辑**：3个wing并行 recall → 拼接 → 注入为系统消息

| Wing | Label | n_results |
|------|-------|-----------|
| wing_code | 技术上下文 | 5 |
| wing_user | 用户偏好 | 5 |
| wing_agent | 固定信息 | 5 |

**问题点**：

① **`n_results=5` 对所有wing一刀切** — wing_code可能有几十条技术结论，但只取5条；wing_user可能只有2条偏好，也取5条（实际返回更少）。应该根据wing的实际抽屉数动态调整。

② **`_MAX_CHARS_PER_WING=2000` 截断风险** — ChromaDB语义搜索返回的每条结果包含完整原文（几百到几千字），5条很容易超2000字。截断后可能丢掉关键信息。

③ **无用户输入相关性过滤** — `auto_recall_memories(user_input=user_input)` 接收了用户输入但不做任何相关性排序，只是无差别取每个wing最新的5条。如果上一轮讨论了A话题，这一轮用户问B话题，仍然会塞入A的记忆造成干扰。

### 2. `_auto_memory.py` — 讨论后自动存储 ⚠️

**触发时机**：`run_loop.py:L154-167`，broadcast结束后、压缩历史前执行

```python
mem_stats = await auto_store_memories(engine, history, topic)
```

**内部逻辑**：3次LLM poll串行 → ChromaDB直接写入

| Poll | Wing | Room命名 | Model |
|------|------|----------|-------|
| Poll1:技术上下文+工具方法 | wing_code | `round-{timestamp}-{topic_slug}` | summarize_model (glm-5.1) |
| Poll2:用户偏好+指令风格 | wing_user | `preferences-{timestamp}` | same |
| Poll3:固定事实+发现规则 | wing_agent | `discoveries-{timestamp}` | same |

**问题点**：

④ **Poll2/Poll3 room名每天覆盖一次** — `preferences-20260527`、`discoveries-20260527`。同一天多次讨论时，后面的会覆盖前面的（ChromaDB dedup by content hash？不对——看代码用的是 `tool_add_drawer`，没有去重逻辑）。实际上每次都会新增一个drawer，但room名相同意味着recall时按room查会混在一起。

⑤ **"无"检测过于粗糙** — `"无" not in content1[:20]`。如果LLM输出开头是"本次讨论主要涉及..."然后中间写了"无相关内容"，照样存入。反之如果LLM第一句就写"无特别发现"，即使后面有实质内容也被跳过。

⑥ **3次poll串行浪费延迟** — Poll1→Poll2→Poll3各需2-5s LLM调用时间，总计6-15s。这三个poll之间没有数据依赖关系，完全可以并行。

## 结论
MemoryPalace 默认轮询逻辑**整体正确，生产可用**。Harper 发现了几个真实问题，但严重度都被他高估了。有一个他**完全搞错**的点需要纠正。

## 关键发现

### 召回侧（`_auto_recall.py`）

**Harper 说"无差别取最新5条"——部分正确但不准确。** 实际调用链：`_recall_wing(wing, n_results=5)` → `MemoryStack.recall()` → `L2.retrieve()` → `col.get(where={wing:...}, limit=5)`。`col.get()` 是按元数据过滤+插入顺序返回，**不是语义搜索**。所以确实是"无语义相关性"，但也不是"最新5条"——是 ChromaDB 内部存储顺序（通常是插入顺序，但不保证）。

**Harper 说"user_input 传了但没用"——正确。** `auto_recall_memories(user_input=user_input)` 接收参数后只拼到 header 里给 agent 看，`_recall_wing` 完全不使用它做过滤。这意味着**每轮群聊注入的记忆完全相同**，不管用户问什么。这是设计上最大的问题。

**2000字符截断——真实但影响有限。** `retrieve()` 内部已经把每条 snippet 截断到300字（L232），5条最多1500字，很少触发2000上限。

### 存储侧（`_auto_memory.py`）

**Harper 说"同一天多次讨论会覆盖"——错误。** `tool_add_drawer` 的 drawer_id 是 `sha256(wing + room + content)[:24]`，**内容不同则 id 不同，不会覆盖**。同一天同 room 下多次讨论会**新增**多个 drawer，不会互相覆盖。Harper 完全没看 `tool_add_drawer` 的幂等逻辑就下了结论。

**"无"检测脆弱——正确但实际影响极低。** LLM 被明确指示"如果某项无内容则写'无'"，实际输出中"无"出现在前20字的概率很高。这个 heuristic 虽然不完美，但够用。

**3次串行——正确，可优化但非必须。** 3次调用之间确实无数据依赖，`asyncio.gather` 可并行。但每次2-5s，串行6-15s 对"讨论结束后"的异步操作来说可接受。

### 其他
- `conversation` 截断12000字、单条800字——合理
- `tool_add_drawer` 有完善的幂等检测（L1160-1179），相同内容不会重复存储
- `run_loop.py` 双层 try/except 兜底，auto_recall 和 auto_store 失败都不阻塞主流程

## 备注
- **唯一值得改的**：`_auto_recall.py` 应该用 `L3.search(query=user_input, wing=wing)` 替代 `L2.retrieve(wing=wing)`，让召回与用户输入语义相关。当前实现等于每轮注入固定记忆，浪费了 user_input 参数
- Harper 对 `tool_add_drawer` 去重机制的判断是错的，需要纠正
- 其余问题都是"可以更好"而非"有bug"
