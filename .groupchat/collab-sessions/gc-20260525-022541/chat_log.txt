## 群聊指令逻辑问题分析

### 🔴 问题1：搜索预算直接矛盾
- **`broadcast_hint.md`**：`单轮网络调用最多3次`
- **`tool_instructions.md`**：Plan A(2次) + Plan B(2次) + Plan C(1次) = **5次**
- 两个文件对同一 agent 的搜索上限给出了不同数字，agent 不知道该听谁的。

### 🔴 问题2：`记忆补充.md` 规则不合理
1. **"任何时刻，达成新成果时，则进行记忆优化"** — 过于激进。每个小成果都触发记忆优化会浪费 token 和时间。
2. **"请编写对应任务脚本，确保后续能直接运行"** — 不是所有成果都需要脚本，这条规则会导致 agent 在简单任务上过度工程化。
3. **"用户要求包含'发送'的任务，必须通过聊天把文件发给用户"** — 与系统限制矛盾（agent 没有原生文件传输能力，只能贴文本）。
4. **"一般发言后如果没有新发现，请使用wait"** — 这条行为规则放在"记忆补充"里语义不对，应该在 `broadcast_hint.md`。

### 🟡 问题3：`broadcast_hint.md` 引用了已废弃的槽位系统
- `发All=3槽，发个人=1槽` — 但 `groupchat_settings.json` 中 `context_pool_capacity: 0`，槽位系统实际是关闭的。这条说明会误导 agent。

### 🟡 问题4：`leader_prompt.md` 终止条件模糊
- `循环>2轮` — "循环"定义不清，是 agent 自身循环还是讨论轮次？
- `讨论3-5轮` — 这是一个范围不是阈值，agent 无法判断到底第几轮该停。

### 🟡 问题5：`output_efficiency.md` 与 `instructions.md` 大量重叠
- 两者都在说"结果给完即停"、"不发空确认"、"直接给结果不铺垫"
- 浪费 token，且两处措辞略有差异可能造成理解歧义

### 🟢 无问题的文件
- `group_nudge.md` — 简洁明确
- `group_context.md` — 纯模板变量，无逻辑
- `coding_principle.md` — 清晰
- `user_context.md` — 简洁
- `memory.md` — 逻辑自洽
