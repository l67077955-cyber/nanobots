[Kirk]: Harper的模型配置不在文件系统里，应该在数据库或运行时配置中。让我直接查运行时配置。同时，我已经收集了足够的信息来回答两个问题。让我整理一下：

1. **Harper报错原因**：`litellm.BadRequestError: OpenrouterException - Provider returned error` — 这是OpenRouter返回的400错误。当前分支(progressive-fixes)相比dev分支，**删除了`timeout=20`的硬超时**。但这个错误不是超时，是BadRequest(400)。400错误在`_detect_compat_issues`中有处理逻辑——会自动检测并drop不兼容的参数（如presence_penalty等）。这个逻辑在两个分支都存在。所以报错更可能是：Harper使用的模型在OpenRouter端临时不可用/下线，或者请求中包含了该模型不支持的参数。

2. **MiniMax M3定价**已获取。

让我把结果发给用户。但首先我需要确认Harper用的是什么模型——从用户的问题上下文看，用户想对比MiniMax M3和Harper当前模型。我无法从文件系统找到Harper的模型配置，但可以从错误信息推断它走的是OpenRouter。

## 结论

**Harper报错原因**：`OpenrouterException - Provider returned error` 是OpenRouter返回的400 BadRequest。对比dev分支，当前progressive-fixes分支在`litellm_provider.py`中**删除了`timeout=20`的硬超时限制**，但这不是400错误的原因。400错误通常由以下原因触发：
1. Harper使用的模型在OpenRouter端临时下线或不可用
2. 请求中包含该模型不支持的参数（如`presence_penalty`、`frequency_penalty`等）——代码中`_detect_compat_issues`有自动降级逻辑，但首次调用仍会报错
3. 模型名称变更或provider路由失败

两个分支在400错误处理逻辑上**无差异**，`_detect_compat_issues`方法完全一致。差异仅在timeout移除。

[Kirk]: ## 结论

auto_recall **召回端风险可控**，你的顾虑主要应放在 **auto_store（存储端）**。dev 分支已修复了之前最严重的 sim 阈值形同虚设问题，但存储质量门槛仍然偏低。

## 关键发现

### ✅ 已修复（dev `44440fb`）
| 问题 | 修复方式 |
|---|---|
| sim阈值形同虚设 | `search_raw` + `sim>0.1` 硬过滤 |
| 关键词黑箱 | LLM生成的关键词现在显示在系统消息中，可审计 |
| 记忆系统元讨论污染 | `_is_self_referential()` 过滤 ≥2个记忆关键词的内容 |
| 重复存储 | `_is_duplicate()` 存储前检查 sim>0.6 |

### ⚠️ 仍存在的风险
1. **LLM关键词质量不稳定** — 模糊输入（如"看看"）时，LLM生成的关键词可能偏离意图。补救：关键词已可见，你可以看到搜了什么
2. **存储质量门槛过低** — 仅 `len>50` 且前20字不含"无"，没有内容质量评分。低质量提取仍会入库
3. **Room粒度粗** — `wing_code` 用 `round-{日期}-{主题slug}`，同主题多轮讨论堆进同一个 room，召回时可能混入过期信息
4. **每次讨论后3次LLM调用** — 增加延迟和 token 消耗（summarize model）
5. **召回注入膨胀** — 3个 wing 各 2000 字符上限，最坏情况往系统消息注入 6000 字符

## 建议

- **保留 auto_recall**：召回端已足够稳健，sim 过滤 + 关键词可见性 = 可控
- **收紧 auto_store**：提高质量门槛（如要求至少2个非空段落）、增加 room 粒度（按子话题分 room）
- **如果暂时不想动代码**：用 `stable-20260527`（`39f1433`）作为回退点，它有 sim 过滤但没有 store 的去重/自我指涉过滤——不过这意味着 store 端更脏，所以其实 dev 更好
