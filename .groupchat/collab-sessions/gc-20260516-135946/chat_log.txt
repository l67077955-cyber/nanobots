## ConversationPool — 信号量插槽池

```
容量 = agent数 × 3（默认），通过 groupchat_settings.json 的 context_pool_capacity 可配置
```

**插槽计费规则：**
- `chatroom_send(to="All")` 发给N个队友 → 消耗 **N 个插槽**
- `chatroom_send(to="Harper")` 发个人 → 消耗 **1 个插槽**
- 池满时 `chatroom_send` 阻塞等待（`ALLOCATE_TIMEOUT=15s`），超时返回 `BLOCKED`

**插槽释放机制（3条路径）：**
1. **正常回复：** `chatroom_send` 调用时检测到 `_last_received_from`，调用 `mark_replied()` → 释放1槽
2. **未回复：** 接收方调用 `wait()` 时不回复 → `release_unread()` → 释放所有未读消息的插槽
3. **wait超时：** `wait()` 返回 timeout → 同上释放

**用户消息特权：**
- `allocate_user()` 强制插槽，不等待，即使超过容量
- 设置 `_user_priority` 事件 → 所有 agent 的 `allocate()` 被立即拒绝

## LeaderGate — 发言次数闸门

```
每个非Leader agent → 每轮Leader发言之间最多发1条
Leader一说话 → 所有计数器归零
```

来源：`chatroom_tools.py` 第564行 `LeaderGate`。

---

## SearchPool — 搜索额度池

```
初始额度 = search_initial (默认2)
每次工具调用(web_search) → 扣1额度
每次 chatroom_send 产出 → 赚0.25额度（分数累积，够1才给）
Leader 可用 transfer_credits 跨 agent 划拨
```

同一次回复中 `queries` 批量搜索只扣1次（批内并发共享 `_batch_lock`）。  
注意这里`chatroom_send`的`on_output`调用在send之后——**发完消息即赚回0.25搜索额度**。


[Kirk]: ## ConversationPool 对话池逻辑

核心思想：**把对话链当有限资源，信号量控制流量，按接收人数计费。**

### 容量
```
capacity = max(n × (n-1), 2)   # n = agent 数量
```
2 agent → 2槽，3 agent → 6槽，4 agent → 12槽。可通过 `context_pool_capacity` 配置覆盖。

### 槽位消耗

| 操作 | 消耗 |
|---|---|
| `chatroom_send(to="All")` 发给3个agent | **3槽** |
| `chatroom_send(to="Harper")` | **1槽** |
| `wait()` 不回复直接等下一条 | **释放所有未读槽** |
| `chatroom_send` 回复发信人 | **释放1旧槽 + 消耗新槽** |

### 三条释放路径

1. **`release_unread(agent)`** — agent 调 `wait()` 时，释放所有未回复的 pending 槽位
2. **`mark_replied(agent, sender)`** — agent 回复某人时，释放该 sender 占的那个槽
3. **超时放弃** — `allocate` 等待超过 15s，自动释放已获取的部分槽

### 用户优先级

`allocate_user()` 强制分配不阻塞。分配期间通过 `_user_priority` Event 阻止 agent 分配，避免竞争。`_available` 可因 user overflow 变负数（设计意图）。

### 池满行为

Agent 的 `chatroom_send` 返回 `BLOCKED: pool full (x/y)`，消息被丢弃。Agent 需调 `wait()` 释放槽位或减少发送目标。

### 数据流

```
ChatroomSendTool.execute()
  → pool.allocate(sender, recipients)   # 消耗槽位
  → pool.mark_replied(sender, from)     # 回复时释放旧槽
  → mailbox.send()                      # 实际投递

WaitTool.execute()
  → pool.release_unread(agent)          # 释放所有未读槽
  → mailbox.wait()                      # 阻塞等待
```

源码位置：`nanobot/groupchat/orchestra/mailbox.py` (ConversationPool 类)，调用方在 `chatroom_tools.py` 的 `ChatroomSendTool` 和 `WaitTool`。

[Harper]: 同意，需求明确了。用户要的就是独立的 pool 而非公用池。

当前 ConversationPool 的 `allocate(sender, recipients)` 从全局池扣 `len(recipients)` 槽。改成:

**每个 agent 持自己的信号量，发送消息从自己的池子里扣。**

```
allocate(A, [B, C])  →  从A的池扣2槽
mark_replied(B, A)   →  还1槽给A的池
release_unread(B)    →  还所有B的pending发信人槽
```

**容量分配（基于已有 rank 体系）：**

| 等级 | 池容量 | 含义 |
|------|-------|------|
| pawn(兵) | 2 | 最多2条消息 pend |
| knight(马) | 3 | 3条 |
| bishop(象) | 3 | 3条 |
| queen(后) | 4 | 4条 |
| leader | rank+1 | 兵leader=3,马leader=4... |

**关键变化：**
1. `ConversationPool.__init__` 接收 `dict[str, int]` 替代 `capacity`
2. 每个 agent 持独立 `asyncio.Semaphore`，`allocate` 从发送方扣
3. `_pending` 记录谁欠谁的，`mark_replied/release_unread` 归还给发送方
4. 总量 = sum(per-agent) 仍受控（4个兵=8总量，比之前4×3=12还紧）

[Harper]: 对，迅游没有GFN专项线路。**要选有GFN专线的加速器**，不然走通用线路延迟高、丢包多。

卡顿问题的原因和排查方案：

## 卡顿原因排查（从上到下）

**① 加速器不对 → 换奇游/UU**
- 迅游没有GFN专项 → 换 **奇游加速器（GFN日服专线）** 或 **UU国际版**
- 必须开加速选日本节点，全程保持

**② GFN串流设置没调 → 手动改码率**
- GFN客户端 → 设置 → 串流质量 → 选 **"自订" / Custom**
  - **解析度**：720p（保流畅）/ 最高1080p
  - **码率**：手动拉到 **15-20Mbps**（低码=花屏，高码=卡顿）
  - **帧率**：60fps
- 默认的"自动"模式在网波动时会频繁降画质，反而更卡

**③ WiFi不稳定 → 换4G/5G再试**
- 卡顿时切换蜂窝数据 vs WiFi 排除本地WiFi问题
- 手机WiFi频段选**5GHz**（2.4GHz干扰大）
- 离路由器近点，隔墙时信号差导致丢包

**④ 开个网络监控**
- 加速器里看实时延迟：如果**>80ms或跳ping**，换节点
- 连续丢包>3% → 换加速器/换运营商网络

## 一句话操作

**换奇游加速器，GFN选日本节点，串流设720p/15Mbps→确认不卡了再慢慢往上涨画质。**
