## [故障分析] AI压缩功能失效 — Root Cause

**根源：两阶段阈值倒置**
| Stage | 作用 | 设定值 |
|---|---|---|
| Stage1 exec_max_chars | exec原始输出上限截断 | **10,000** |
| Stage2 summarize_threshold | AI压缩触发门槛 | **20,000** |

Stage1已经把输出压到≤10k了，Stage2却要求在≥20k时才启动AI压缩 → **死锁式永不命中**

**次要风险：模型路由**
`z-ai/glm-5.1` — litellm需要对应provider支持才能跑通，否则即便进入压缩也会异常回退到纯丢弃(drop)。

**影响范围：**
所有超出阈值的工具输出都走了静默丢弃路线(`_head_tail_truncate`)，而不是语义化AI摘要。上下文窗口里的历史信息因此严重碎片化。

修复方向二选一：
1️⃣ `summarize_threshold`降到 ≤ `exec_max_chars`（比如设成8000）  
2️⃣ 或者在stage1的逻辑里加判断：如果启用了AI compression就不做机械截断而是留长传给stage2处理

[Harper]: 好分析。补两个你没提到的点：

**1. 功能2的路由必然炸**

你用 `z-ai/glm-5.1` 通过 openrouter 调 — OpenRouter 的标准模型名是 `openai/gpt-4o-mini` 这类格式，不存在裸叫 `z-ai/*` 就能通的道理。等到消息数攒够21条触发 `maybe_compress()` 的那一刻，litellm会抛出类似 `ModelNotFound/AuthenticationError` 的异常，然后走 catch-all fallback → **直接丢掉中间消息不做摘要**。这不是"待验证"，这是确定性事件。

**2. 更深层的设计矛盾**

你说功能1是死代码没错，但这暴露了一个架构问题：为什么要造一个不会跑的stage2 AI压缩器？合理的推测是——

最初设计了两步流水线：
```
原始输出 → stage1: exec_max_chars机械截断 → stage2: AI语义压缩
```

后来某次重构改了stage1的实现（加了 `_head_tail_truncate`），但忘记把stage2接到管线上去了。或者说有人以为 `summarizer.py` 已经被集成进 pipeline 但其实并没有。

这就解释了用户的困惑："我看日志觉得有问题" — 他看到的是配置里有AI压缩、日志里也有相关的logger语句（编译时的模块加载打印），但运行时从来没真正起过作用。

---

综上：**两个功能的根因不同但后果一致 — AI压缩等于摆设。** 
功能1是接线断了（dead code），功能2是一旦通电必烧保险丝（模型路由不通）。
---
[Kirk]: ## 诊断结论

两个独立的"AI压缩"功能，各有各的问题：

### 1. 工具输出AI摘要 (`summarizer.py`) — 死代码
函数写好了、配置也配了（`summarize_threshold: 20000`），但**整个代码库没有任何地方调用它**。当前工具输出走的是 `result_processor.py` 的机械截断（硬切到 10k 字符）。

### 2. 历史消息AI压缩 (`context.py`) — 模型路由必炸
代码路径是通的，消息数达到 21 条时会触发。但配置的压缩模型是 `z-ai/glm-5.1`，LiteLLM 会把它路由到 `zhipu` provider——而 **zhipu 的 API key 是空的**（唯一有 key 的 provider 是 openrouter）。

实际执行链：
```
触发压缩 → 调用 z-ai/glm-5.1 → zhipu 无 key → 异常
→ catch → "AI compress failed, falling back to drop"
→ 中间消息被静默丢弃，无摘要
```

### 修复方向
| 问题 | 修复 |
|---|---|
| summarizer.py 未接入 | 在 `result_processor.py` 中 import 并调用 |
| 模型路由不通 | `summarize_model` 改成 openrouter 支持的模型，如 `openrouter/google/gemini-2.0-flash-001` |
