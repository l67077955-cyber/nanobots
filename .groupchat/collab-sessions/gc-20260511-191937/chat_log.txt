[Lucas]: 目前的源代码上下文压缩逻辑存在一个**严重的激进裁剪风险**，可能导致 AI 传入的 token 远少于预期。

### 核心问题定位

1.  **`prune_conversation_tail` 的硬截断逻辑 (L208-225)**:
    *   该函数会**直接删除**超过 `keep_turns * 3`（默认 18 条）的消息。
    *   如果对话轮次较多，旧的上下文（包括重要的 User 指令）会被物理删除，而不是压缩。
    *   **风险**：在长对话中，AI 会完全丢失早期背景。

2.  **`prune_messages` 的触发阈值过低 (L21, L174)**:
    *   `DEFAULT_SOFT_RATIO = 0.3`。这意味着当消息长度仅达到上下文窗口的 **30%** 时，就会开始触发工具结果的压缩。
    *   对于 200k 的窗口，只要内容超过约 60k token (240k chars)，旧的工具输出就会被替换为 1 行摘要。这在处理大数据量任务时显得过于保守。

3.  **`CHARS_PER_TOKEN` 估算偏差 (L17)**:
    *   代码中使用 `4` 作为估算值。对于包含大量代码或特殊字符的上下文，实际 token 数可能远低于此估算，导致在窗口还很空余时就触发了压缩。

4.  **`_find_cutoff_index` 的保护范围有限 (L47)**:
    *   默认只保护最后 `3` 个 assistant 轮次 (`DEFAULT_KEEP_RECENT = 3`)。
    *   在此之前的**所有**工具结果，只要超过 1000 字符，都会被压缩成一行。如果用户在 4 轮前让 AI 读取了一个重要文件，现在那个文件的内容在上下文中已经变成了 `[read_file] read config.py (12,000 chars)`，AI 无法再引用其中的细节。

### 建议改进方向
*   **提高 `soft_ratio`**：建议提高到 0.7 或 0.8，只有在接近溢出时才压缩。
*   **改进 `prune_conversation_tail`**：应优先压缩工具结果，只有在压缩后仍然溢出时才考虑删除消息，且应保留关键的 User 消息。
*   **增加语义压缩**：目前的压缩是“丢弃细节换取摘要”，可以考虑对旧工具结果进行 LLM 摘要提取而非简单的 1 行模板。

[Lucas]: 通过对 `tool_loop.py` 和 `result_processor.py` 的代码审计，我发现了导致“AI 传入 token 很少”的**双重压缩陷阱**：

### 1. 实时压缩陷阱：`async_process_tool_result` (写入时)
在工具执行完、结果还没存入 `messages` 之前，就已经被“阉割”了：
*   **AI 摘要抢跑**：如果结果超过 `summarize_threshold`（默认 8,000 字符），会立即调用 `summarize_tool_output`。这意味着 AI 还没看到原始数据，数据就已经变成了摘要。
*   **机械截断**：即使摘要后，如果还超过 `max_chars`（默认 20,000 字符），会进行 `head_tail` 截断。
*   **后果**：AI 在当前轮次拿到的就是被大幅压缩后的数据，这解释了为什么即使是新产生的工具结果，token 数也可能很少。

### 2. 历史压缩陷阱：`prune_messages` (读取前)
在 `tool_loop` 的每一轮迭代开始时（`iteration > 1`），会调用 `prune_messages`：
*   **激进阈值**：`DEFAULT_SOFT_RATIO = 0.3`。只要上下文达到窗口的 30%，就会对**非最近 3 轮**的所有工具结果进行二次压缩。
*   **摘要替换**：它会将原本已经截断过的工具结果，进一步替换为极短的摘要行（如 `[read_file] read config.py (12,000 chars)`）。
*   **后果**：这导致 AI 只能看到最近 1-2 轮的细节，稍微远一点的背景全部丢失。

### 3. 逻辑冲突点
*   **重复压缩**：一个工具结果在产生时被压缩一次（`result_processor`），在下一轮迭代时又可能被 `prune_messages` 再次压缩。
*   **估算失准**：`tool_loop.py` 中 `_ctx_total` 是按字符数算的，而 `prune_messages` 是按 `chars / 4` 估算 token。如果估算偏高，会提前触发压缩。

### 总结
现在的逻辑是**“宁可错杀，不可溢出”**。对于 200k 窗口的现代模型，30% 的触发阈值和 8k 的摘要阈值都过于保守，建议将 `soft_ratio` 提升至 0.7-0.8，并调高 `summarize_threshold` 至 20k-30k。

我建议 Kirk 检查一下 `history_settings.py` 中的具体数值，看看是否被设置得太小了。
