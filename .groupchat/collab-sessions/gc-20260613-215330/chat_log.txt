## 关键发现

### 三层压缩机制

| 层级 | 机制 | 触发条件 | 压缩方式 |
|------|------|----------|----------|
| 一 | `HistoryContext.compress_messages()` | 消息数 ≥ max×0.7 | AI摘要替换中间消息 |
| 二 | `tool_pruning.prune_messages()` | tool loop第2次迭代 | 旧工具输出→1行摘要 |
| 三 | `prune_conversation_tail()` | token超限 | 尾部消息AI摘要，附加到system末尾 |

### 压缩→重复操作统计

- **总会话**：993 | **有压缩**：31（3.1%）| **总压缩事件**：52次
- **总重复工具调用**：668次 | **压缩后重复**：52次 | **关联率**：7.8%

### 最严重案例

- `gc-20260514-121443`：1次压缩 → 10次重复（Lucas反复exec/read_file同一文件）
- `gc-20260610-153045`：1次压缩 → 9次重复（Retriever反复grep同一代码）
- `gc-20260613-143432`：1次压缩 → 5次重复（Kirk反复grep同一关键词）

### 根因分析

1. **AI摘要丢失工具调用细节**：`read_file`的具体行号、`exec`的完整输出被压缩后，AI不知道已读过/执行过，重新操作

- 7.8%的关联率说明大部分重复调用并非压缩导致（可能是AI本身的规划问题），但压缩确实加剧了重复

[Harper]: 看完代码，发现配置和算法存在多个问题：

## 🔴 严重问题

### 1. 配置不一致（配置漂移）

| 参数 | history_settings.py | history_settings.json | 影响 |
|------|---------------------|----------------------|------|
| `max_messages` | 50 | **30** | 运行时更严格 |
| `max_context_chars` | 100,000 | **30,000** | 运行时小3倍 |
| `compress_ratio` | 0.8 | **0.7** | 更早触发压缩 |
| `compress_max_summary_tokens` | 600 | **缺失** | 回退到默认值 |

`json` 覆盖了 `py` 的默认值，导致实际运行时参数与预期不符。

### 2. `maybe_compress` 摘要插入位置错误（context.py:301-310）

```python
for i, m in enumerate(self.messages):
    if i in all_protected:
        rebuilt.append(m)
    elif not summary_inserted:
        rebuilt.append(summary_msg)  # 插入位置依赖遍历顺序
```

当 `keep_user_messages=True` 时，protected head indices 是非连续的。摘要会插入到"第一个可压缩消息的位置"，但这个位置可能是中间任意位置，破坏消息顺序逻辑。

### 3. `history_to_messages` 强制保护所有 user/system（message_converter.py:141-142）

```python
elif m["role"] in ("user", "system"):
    critical.append(m)
```

与 `context.py` 的 `_find_head_indices` 逻辑不一致：
- `context.py`：只保护 index 0 + 第一个 user
- `message_converter.py`：保护所有 user/system

长对话时 message_converter 会保留过多 user 消息，导致 assistant 消息被过度裁剪。

## 🟡 中等问题

### 4. `tool_pruning` 摘要丢失关键上下文（tool_pruning.py:96-106）

```python
if tool_name == "exec":
    return f"[exec] ran `{cmd}` -> exit {exit_code}, {line_count} lines output"
if tool_name == "read_file":
    return f"[read_file] read {path} ({content_len:,} chars)"
```

**问题**：
- `exec` 只保留 exit code，丢失了 stderr 输出、错误原因
- `read_file` 只保留路径和大小，丢失了具体行号范围（offset/limit）
- AI 看到摘要后无法判断"这个文件我已经读过了，且行号范围是 X-Y"

### 5. `age_tool_log` 只保留第一行（message_converter.py:48）

```python
first_line = preview.split("\n")[0][:100]
```

对于 `exec` 命令，第一行通常是命令本身或空行，真正的错误信息在第二行开始。这导致错误诊断信息被丢弃。

### 6. `prune_conversation_tail_with_summary` 追加到 system 消息（tool_pruning.py:313）

```python
messages[last_sys_idx]["content"] = parts[0] + summary_block
```

将摘要追加到 system 消息末尾，但：
- system 消息通常只关注开头指令
- 追加后 system 消息可能过长被截断
- 摘要容易被 AI 忽略

### 7. `history_to_messages` 省略提示插入位置错误（message_converter.py:187-190）

```python
result.insert(insert_pos, {  # insert_pos = 0
    "role": "system",
    "content": _OMISSION_PROMPT,
})
```

省略提示插入到消息列表最前面（index 0），但 index 0 通常是 system prompt。这会导致省略提示覆盖真正的 system prompt。

## 🟢 建议修复

| 优先级 | 问题 | 修复方案 |
|--------|------|----------|
| P0 | 配置漂移 | 同步 `history_settings.json` 与 `history_settings.py` 默认值 |
| P0 | 摘要插入位置 | 改为插入到 head 和 tail 之间，保持相对顺序 |
| P1 | tool_pruning 摘要 | `read_file` 保留 offset/limit；`exec` 保留最后一行 stderr |
| P1 | message_converter 保护逻辑 | 与 context.py 保持一致（只保护 index 0 + 第一个 user） |
| P2 | age_tool_log | 保留最后一行（通常是错误信息）而非第一行 |
| P2 | system 消息追加摘要 | 改为插入独立 system 消息或插入到 user 消息之前 |
