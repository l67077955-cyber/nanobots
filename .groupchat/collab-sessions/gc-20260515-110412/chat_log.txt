[Harper]: ## 当前上下文组织形式 — 4 层流水线

```
用户输入
  │
  ▼
Stage 1 ─ 工具输出截断
  │  exec: 10k chars | web_fetch: 8k | web_search: 5k
  │  HTML 检测 → 标记不可用
  ▼
Stage 2 ─ 工具结果 AI 摘要
  │  >8k chars → gpt-4.1-nano 摘要 → ≤4k chars
  ▼
Stage 3 ─ 对话历史窗口 (HistoryContext)
  │  max 50 条 / 100k chars
  │  头部保护: system prompt + 所有用户消息永不删除
  │  尾部保护: 保留最近 6 条
  │  中间区域: 达到 80% 阈值 → AI 摘要或直接丢弃
  ▼
Stage 4 ─ 迭代上下文裁剪 (tool_loop 第2轮+)
  │  软裁剪 30% | 硬裁剪 50%
  │  保留最近 3 条
  ▼
LLM 调用
  │  cache_control 只打在 system messages 上
  │  前缀 = system prompt 块，永不增长
  ▼
输出
```

**关键参数**（`~/.nanobot/history_settings.json`）：

| 参数 | 值 | 作用 |
|------|-----|------|
| `max_messages` | 50 | 历史消息上限 |
| `max_context_chars` | 100k | 历史字符上限 |
| `compress_ratio` | 0.8 | 达到 40 条触发压缩 |
| `compression_keep_recent` | 6 | 压缩时保留最近 N 条 |
| `keep_user_messages` | true | 保护所有用户消息不被删 |
| `context_window_tokens` | 200k | LLM 上下文窗口 |

**三层保护机制**确保关键信息不丢失：
1. **头部保护** — index 0 (system prompt) + 所有用户消息
2. **尾部保护** — 最近 6 条消息
3. **中间压缩** — AI 摘要替代原始对话，而非直接丢弃

**前缀稳定**（Kirk 已分析）：`_sys_msg_count` 快照固定前缀边界，cache_control 只打在 system 消息上，对话历史增长但前缀不变 → 缓存命中。

[Kirk]: ## 当前上下文组织形式 — 完整架构

整个上下文从存储到发送给 LLM，经过 **4 层处理**：

### 第 1 层：HistoryContext（原始存储）

`context.py` — 以 `[{sender, content}, ...]` 格式存储所有群聊消息。触发压缩时（消息数 ≥ `max_messages × compress_ratio`，即 30×0.7=21 条）：

```
┌──────────────────────────────┐
│  Head（受保护）              │ ← 连续 system 消息 + 所有 user 消息
├──────────────────────────────┤
│  Middle（可压缩）            │ ← AI 摘要 或 直接丢弃
├──────────────────────────────┤
│  Tail（受保护）              │ ← 最近 6 条（compression_keep_recent=6）
└──────────────────────────────┘
```

### 第 2 层：Prompt Builder（组装 LLM 消息）

`prompt_builder.py:629-712` — 按 `prompt_order.json` 顺序拼接：

```
┌──────────────────────────────┐
│  persona / memory / tools    │ ← system messages（stable_tpl_vars）
│  hard_rules / examples ...   │   变量替换用 stable 值
├──────────────────────────────┤
│  history（对话历史）         │ ← message_converter 转换
├──────────────────────────────┤
│  [datetime] + [round]        │ ← volatile_tpl_vars，放最后
└──────────────────────────────┘
```

关键：history 之前的 system 组件用 `stable_tpl_vars`（agent 名、成员列表等不变值），history 之后的 volatile 变量（时间、轮次）单独追加，**不破坏前缀稳定性**。

### 第 3 层：Broadcast（运行时快照）

`broadcast.py:685` — agent 启动时拍快照：

```python
_sys_msg_count = len(messages)  # 此后前缀永不修改
```

此后所有裁剪操作（tool_pruning、中断处理）只动 `messages[_sys_msg_count:]`。

### 第 4 层：cache_control 注入

`litellm_provider.py:198-235` — 发送前只给 system messages 打 `cache_control: ephemeral`：

```
配额：4 个 breakpoint → tools 占 1 → system 占 3
只标记最后 3 条 system 消息
user/assistant 消息永远不加
```

---

### 为什么前缀不逐步增加

| 机制 | 作用 |
|---|---|
| `_sys_msg_count` 快照 | 前缀边界固定，永不修改 |
| stable vs volatile 变量分离 | 前缀内容不变 |
| cache_control 只打 system | 服务端缓存点不随对话移动 |
| 裁剪只动尾部 | `prune_conversation_tail` 只裁 `messages[sys_msg_count:]` |
| 对话窗口固定 | 保留最近 6 轮（`_CONV_KEEP_TURNS=6`），超出丢弃 |

**结果**：system prompt 块永远 ~几千 token，Anthropic 每次请求都命中缓存，跳过前缀的 KV 重复计算。对话历史在下面自然增长但被定期裁剪到固定窗口。

[Kirk]: ## 结论

上下文组织是 **4 层流水线**，每层各司其职，最终通过前缀稳定机制让 Anthropic prompt cache 持续命中。

## 关键发现

**4 层流水线：**

| 层 | 位置 | 作用 |
|---|---|---|
| ① 工具结果截断 | `result_processor.py` | exec 10k / web_fetch 10k / web_search 5k |
| ② HistoryContext | `context.py` | 存储 30 条/50k chars，≥21 条触发压缩（head 保护 + middle 摘要 + tail 保留 6 条） |
| ③ Prompt Builder | `prompt_builder.py` | stable 变量放前缀，volatile 变量（时间/轮次）放末尾 |
| ④ Broadcast 快照 | `broadcast.py:685` | `_sys_msg_count` 固定前缀边界，裁剪只动尾部 |

**前缀稳定机制（为什么前缀不增长）：**
- `_sys_msg_count` 快照 → 前缀边界永不修改
- `cache_control` 只打 system 消息（4 breakpoints：tools 占 1，system 占 3）
- `tool_pruning` 只裁 `messages[sys_msg_count:]`，保留最近 6 轮
- stable vs volatile 变量分离确保前缀内容不变

**实际配置（`~/.nanobot/history_settings.json`）：**
- `max_messages`: 30，`max_context_chars`: 50,000，`compress_ratio`: 0.7
- `context_window_tokens`: 35,000
- `context_pruning`: soft_ratio=0.4, hard_ratio=0.4, keep_recent=3

## 备注

工具结果 AI 摘要阈值（20,000 chars）大于截断上限（10,000 chars），摘要可能永不触发——疑似配置 bug。
