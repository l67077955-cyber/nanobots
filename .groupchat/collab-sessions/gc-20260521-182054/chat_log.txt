[Harper]: 分析到位。补充一个关键细节：

**Stage1（tool_pruning.py）的 `prune_messages` 实际上有双阶段修剪**，不只是单层规则替换：

1. **Soft pruning**（触发条件：`ratio >= soft_ratio(0.3)`）→ 只动 `cutoff` 之前的 `role=="tool"` 消息，且只替换超过 `soft_max_chars(1000)` 的大结果
2. **Hard cap**（触发条件：`total_chars > hard_max_total_chars(50,000)`）→ **突破 keep_recent 保护**，从最旧开始强制精简所有 tool result

这就是为什么即使最近3轮也被保护，极端情况仍有兜底——hard cap 是最后的安全阀，它无视 keep_recent 屏障。

另外 `prune_conversation_tail_with_summary` 还有个隐藏的 `min_dropped_for_summary=5` 阈值——丢弃少于5条时不调LLM，直接静默丢弃，省一次API调用。

三层管线+hard cap+min_dropped阈值，整体设计在token预算和信息保留之间的权衡做得相当务实。

[Kirk]: ## 结论

nanobot 的总结机制是 **4 阶段渐进式上下文压缩管线**，从轻量截断到 AI 摘要逐级升级：

```
工具输出 → Stage1: 逐工具截断 → Stage2: AI摘要 → Stage3: 上下文修剪 → Stage4: 历史压缩
```

## 关键发现

### Stage 1 — 逐工具截断 (`result_processor.py`)
- 工具输出超过 `summarize_threshold`(8,000字符) 时触发
- 受全局开关 `summarize_enabled` 控制

### Stage 2 — AI 摘要 (`run_loop.py:generate_summary()`)
- 调用 `summarize_model`(默认 gpt-4.1-nano) 对大工具输出做 AI 压缩
- 输入限制 8,000 字符，输出限制 4,000 字符

### Stage 3 — 上下文修剪 (`tool_pruning.py:prune_messages()`)
- **Soft pruning**：超过窗口 30% 时，保护最近 3 轮，将旧 tool result 替换为 1 行摘要（工具类型感知模板）
- **Hard cap**：总字符仍超 50,000 时无视保护，从最旧开始强制压缩

### Stage 4 — 历史压缩 (`tool_pruning.py:prune_conversation_tail_with_summary()`)
- 对话超 `keep_turns*3` 条时，丢弃早期消息前调 LLM 生成结构化摘要
- 摘要追加到最后一条 system 消息末尾（保持 DeepSeek prefix cache）
- 按 `[上下文摘要` 分割符替换旧摘要防累积

### 输出质量校验 (`component_manager.py`)
- 空总结 / 元信息 / 深度不足三重检测

### 核心文件
| 文件 | 职责 |
|---|---|
| `history_settings.py` | 配置中心（所有开关/阈值） |
| `result_processor.py` | Stage 1 入口 + 开关穿透 |
| `run_loop.py` | Stage 2 AI 摘要调用 |
| `tool_pruning.py` | Stage 3-4 裁剪 + 尾部摘要 |
| `context.py` | 中间区域 AI 压缩 |
| `component_manager.py` | 输出质量校验 |
