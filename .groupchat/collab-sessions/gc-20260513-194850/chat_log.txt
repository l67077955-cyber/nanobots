可见性逻辑框架

核心原则

用户可见层 = 唯一交付通道。 所有内部系统（memory_palace、chatroom_send、exec、搜索）都是中间件，不是交付终点。

三层可见性模型

用户请求
    │
    ▼
┌─────────────────────┐
│  Layer 1: 采集层     │  ← web_search, web_fetch, exec
│  (用户不可见)         │     结果只存在于agent上下文
└────────┬────────────┘
         ▼
┌─────────────────────┐
│  Layer 2: 协作层     │  ← chatroom_send, memory_palace
│  (用户不可见)         │     agent间交换、持久化存储
└────────┬────────────┘
         ▼
┌─────────────────────┐
│  Layer 3: 交付层     │  ← message() 文本回复
│  (用户可见 ✅)        │     唯一面向用户的输出
└─────────────────────┘


强制规则

#  规则           触发点            检查内容                                         
─  ─────────────  ────────────────  ─────────────────────────────────────────────────
1  交付前置检查   end_discussion前  最终文本是否包含用户请求的实际数据（非元描述）   
2  禁止纯引用     最终回复          不得仅写"已存入memory"或"结果已发给队友"         
3  数据内联       所有回复          实际数据必须出现在文本中，不能只存在于附件/链接  
4  token预算校验  回复生成时        如果回复token < 用户请求数据的最小合理长度 → 拦截

检查清单（end_discussion前执行）

□ 用户请求的具体数据是否出现在最终文本中？
□ 如果用户要"2个地址"——文本中是否有2个完整地址？
□ 如果用户要"总结"——文本中是否有总结内容？
□ 是否有任何关键数据仅存在于memory/chatroom/exec中？
□ 回复token是否足够承载请求的数据量？


根因修复

当前系统缺少一个 交付门控（Delivery Gate）——在 end_discussion 之前自动校验最终回复是否包含用户请求的实际内容。建议在系统层加入：

end_discussion() {
    if (final_response 不含用户请求的实际数据) {
        BLOCK → "交付失败：数据未出现在用户可见层"
    }
}


这个案例的映射

用户请求: 2个LA地址
  ↓
Harper搜索 → 5条结果 [Layer 1, 用户不可见]
  ↓
Kirk存memory → 111字地址 [Layer 2, 用户不可见]  
  ↓
最终回复: "完成。" [Layer 3, ❌ 无地址]
  ↑
违反规则#1、#3、#4


结论：可见性逻辑的核心是——所有内部操作的结果，必须在最终文本回复中有一份完整副本。 内部系统是工作台，不是展示柜。

### 修正后的三层模型

```
Layer 1: 采集层     web_search, web_fetch, exec          → 用户可见摘要（非全文）
Layer 2: 协作层     chatroom_send                         → 用户可见 ✅ 全文
Layer 2b: 存储层    memory_palace.store(visible=false)    → 用户不可见 ❌ 唯一黑洞
Layer 3: 交付层     LLM文本回复                            → 用户可见 ✅
```

**唯一真正的数据黑洞是 `memory_palace.store`（默认 visible=false）。**

### Delivery Gate 调整

原方案检测"最终文本是否包含实际数据"方向正确，但需要加一条专门针对 memory_palace 的规则：

```
end_discussion() {
    if (memory_palace.store 被调用 AND visible=false) {
        if (最终文本不包含与store内容对应的实际数据) {
            BLOCK → "数据存入了memory但未出现在用户可见层"
        }
    }
}
```

因为 `chatroom_send` 已经自动可见，不需要额外检测。`exec`/`web_search`/`web_fetch` 的结果摘要也自动可见。**唯一需要门控的就是 memory_palace.store 这个单向阀。**

[Harper]: 同意。Tier 4a 的逻辑过于粗糙——**只要有 memory_palace 就怀疑，不管文本是否已自足。**

修正后的判断树应该是这样：

```
if ("memory_palace" in tools_used):
    if (文本长度 >= MIN_SUBSTANTIVE_LEN OR 文本包含用户请求的实际数据):
        PASS ✅  # 文本已自足，存mem只是备份
    elif (tools_used中除了memory_palace外还有其他实质工具):
        PASS ✅  # 有其他工具兜底，数据可能在那些工具的可见摘要里
    else:
        FAIL ❌  # memory_palace是唯一信息来源，文本又不够
```

也就是说，**memory_palace 不应成为怀疑标签，只有在它是唯一信源且文本不足以承载请求时才该拦。**

另外还有一个边缘情况需要考虑：如果用户请求的是"记住某句话"这种天然只需要 memory_palace 的操作，Tier 4a 也会误杀。这种情况下应该白名单放行。

[Kirk]: ## 结论

Delivery Gate 已实现。`synthesis_quality_check()` 新增 Tier 4，在 end_discussion 前检测"数据存了但没交付"的情况并强制拦截重试。

## 关键发现

**改动文件：**
- `component_manager.py` — 新增 Tier 4a（memory_palace 黑洞检测）+ Tier 4b（数据工具无对应证据检测）+ 2个专用警告模板
- `broadcast.py` — 传入 `tools_used=all_tools_used`，失败时按原因选精确模板

**可见性修正（Harper 源码验证）：**
- `chatroom_send` → ✅ 全文可见（非黑洞）
- `memory_palace.store(visible=false)` → ❌ 唯一黑洞
- `exec` → 仅55字符预览
- `web_search` → 仅结果数量

**测试矩阵（8/8 通过）：**

| 场景 | 预期 | 实际 |
|------|------|------|
| memory only + "完成。" | ❌ 拦截 | ❌ ✅ |
| memory + 内联地址数据 | ✅ 放行 | ✅ ✅ |
| memory+search + 空文本 | ❌ 拦截 | ❌ ✅ |
| search + 无数据 | ❌ 拦截 | ❌ ✅ |
