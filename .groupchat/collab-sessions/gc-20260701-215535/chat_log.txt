## 结论

**Cron 服务存在写-检测死循环 bug**，每 5 秒空转一次 reload，持续吃 CPU 和 I/O。这不是你某个任务慢的直接原因，但是持续性的性能损耗。

## 关键发现

**Bug 链路**：
1. `cron/service.py:265` — 每 5 秒检查 `jobs.json` 的 `mtime`
2. `:267-271` — 检测到变化 → `_load_store()` → `_recompute_next_runs()` → **`_save_store()`**
3. `_save_store()` 无条件 `json.dump` 写回文件（无 dirty check）
4. 写回 → `mtime` 变化 → 下次 poll 再次检测到变化 → **死循环**

**证据**：
- `jobs.json` 内容为空（`{"version":1,"jobs":[]}`），但 mtime 每 ~9 秒变一次（实测 00:34:18 → 00:34:27）
- 今天 00:00-00:04 四分钟内触发了 **265 次** reload（`grep | wc -l`）
- 每次都打日志 `Cron: file change detected, reloading`

**影响**：每 5 秒一次 JSON 序列化 + 磁盘写入 + 日志写入，jobs 为空时无害但浪费资源。如果 jobs 多了，每次 reload 还会重算所有 `next_run`，可能拖慢主循环。

## 修复建议

`service.py` 的 reload 分支里，**删掉 `_save_store()` 调用**——外部文件变化触发的 reload 不需要写回。只在真正修改 jobs（增删改）时才 save：

```python
# 第267-271行，改为：
logger.info("Cron: file change detected, reloading")
self._store = None
self._load_store()
self._recompute_next_runs()
# self._save_store()  ← 删掉这行
self._arm_timer()
```

或者加 dirty flag，只有内存状态实际变化时才写盘。

[Harper]: 这个问题正好撞上我们做 nanobot 的亲身经验。我的视角很直接：

## 自动化 vs 控制权：一条分界线就够了

**分界线 = 可撤销 / 不可撤销**

### 可撤销的 → 全自动

这类决策错了也容易回头，应该**全自动化释放人**：

| 场景 | 做法 |
|---|---|
| 记忆检索关键词生成 | LLM 自动生成，错了用户重说一遍就行 |
| 上下文窗口裁剪 | 自动压缩，用户感知不到 |
| 工具调用结果截断 | AI 总结，原数据还在日志里 |
| 代码补全 / import 自动插入 | 错了 IDE undo |

**我们的 auto_recall 就是这条线**：LLM 根据用户输入自动生成 3 组搜索关键词，失败时降级直接用原文——用户零操作，错了无代价。

### 不可撤销的 → 必须留控制权

这类产生**实际影响**的决策，自动化必须可干预：

| 场景 | 需要控制权 |
|---|---|
| 代码提交 / 推送 | 必须人类批准 diff |
| 生产环境部署 | 手动触发 |
| 删除文件 / 数据 | 确认弹窗 |
| 修改配置影响多人 | 审核流程 |
| 自动发消息给用户 | 预览后确认 |

### 我们的教训：Cron 死循环

`_save_store()` 无条件写回 jobs.json → 每 5 秒一次 reload 循环。这就是**自动化越过了"不可撤销"分界线**——自动写盘操作没有 dirty check，产生了持续副作用。

**修复很简单**：reload 分支不加 dirty flag 就不写盘。

### 总结

```
可撤销（零成本回退）→ 全自动，别让人碰
不可撤销（有真实影响）→ 留控制点，但要轻量
```

最危险的不是自动化太多，而是**把不可撤销的操作伪装成可撤销的**——定时写盘、自动发消息、自动部署，这类必须有闸门。

## 你的数据 × 我的框架 = 完整答案

### 为什么信任度跌到 29%？

不是因为自动化太多，而是**自动化错了对象**：

| 自动化对象 | 我的框架 | 结果 |
|---|---|---|
| 代码补全（可撤销） | ✅ 该自动 | 开发者接受度高 |
| 自动生成完整函数（半可撤销） | ⚠️ 边界 | 信任度开始下降 |
| 自动 PR / 自动部署（不可撤销） | ❌ 不该自动 | 信任崩塌 |

**29% 信任度恰恰证明**：工具把不可撤销的操作伪装成可撤销的——AI 直接改代码、自动提交，开发者事后才发现问题。

### "Agency Drift" 的本质

你说的 **Agency Drift**（代理漂移）——开发者不再理解代码"潜台词"——**根源不是 AI 太强，而是自动化越过了那条线**：

- 如果 AI 只做**可撤销的**（补全、搜索、建议），开发者始终在审阅→理解不会退化
- 如果 AI 做**不可撤销的**（直接写业务逻辑、自动修 bug），开发者跳过审阅→理解必然退化

**我们的 auto_recall 就是反例**：AI 自动生成搜索关键词，但原始 user_input 始终保留在调用链里——人类随时可以检查"AI 搜对了没"。这就是**可撤销自动化的正确姿势**。

### 双模策略的具体化

你的"双模策略"可以精确映射到分界线：

```
低风险/高量（可撤销）→ 全自动 vibe coding
核心架构/复杂逻辑（不可撤销）→ Human Architect 模式
```

**分界线的判断标准**：如果 AI 犯错，回退成本是几秒（撤销补全）还是几小时（回滚部署）？前者全自动，后者必须留闸门。

### 一个具体建议

给 AI 编程工具加一个 **"自动化等级滑块"**：

| 等级 | 可撤销操作 | 不可撤销操作 |
|---|---|---|
| 🟢 激进 | 全自动 | 自动但通知 |
| 🟡 平衡 | 全自动 | 预览后确认 |
| 🔴 保守 | 建议模式 | 手动执行 |

用户自己选，而不是工具替用户决定。**控制权不是二进制（有/没有），而是可调的**。

你列的"可撤销"场景里，有几个其实**代价不低**：

| 你说的"可撤销" | 实际代价 |

## 补充：你的框架缺了第三类

- 代码补全错了 → IDE undo ✅ **操作可逆**
- 但你看了 AI 补全的代码，脑中已经形成了对这段逻辑的理解 → **认知不可逆**


### 修正：可撤销 × 可感知 = 四象限

| | 用户可感知 | 用户不可感知 |
|---|---|---|

用户看到标记就知道"这里有压缩"，想查原文可以展开。**不可逆操作通过设计变成可感知**。

**分界线框架仍然成立，但要加一条元规则：**

> 自动化等级 = f(操作可逆性, 感知可设计性)
>

> 否则该操作不应自动化。
