## [补充] 对 Kirk 方案的验证与细化

### 1. 零宽字符确实难以伪造

- LLM 需要精确复现 Unicode codepoint，而非语义等价物

[Kirk]: ## 结论

用**零宽不可见字符**（`\u200B` + `\u2060`）作为工具调用记录块的前后缀标记，配合代码层正则过滤，彻底解决 LLM 伪造工具调用格式的问题。LLM 在自然文本生成中几乎不可能自发输出零宽字符序列，这是确定性防御而非概率性禁止。

## 关键发现

**1. 问题本质**
LLM 从 system prompt 和训练数据中学会了工具调用的文本格式（`• exec(...) → ...`），在普通文本回复中模仿该格式"假装执行了操作"。当前 prompt 禁止条款只覆盖了 XML 标签和方括号格式，未覆盖项目符号格式。

**2. 三层防御方案（已实现）**

| 层 | 机制 | 可靠性 |
|---|---|---|
| **Prompt** | 禁止条款明确列出 `• tool(...)` 格式 | 概率性 |
| **零宽标记** | 工具调用记录块用 `\u200B\u2060` 前缀 + `\u200B` 后缀包裹 | 确定性（LLM 无法伪造零宽字符） |
| **正则过滤** | `response_cleanup.py` 中用正则匹配并剥离任何伪造的工具调用格式 | 确定性兜底 |

**3. 为什么零宽字符有效**
- `\u200B`（Zero-Width Space）和 `\u2060`（Word Joiner）在 tokenizer 中是独立 token
- LLM 训练数据中自然语言不包含这些字符，生成概率趋近于零
- 即使 prompt 中有 few-shot 示例，LLM 也需要精确复现 Unicode codepoint，而非语义等价物

**4. 已完成的代码改动**
- `response_cleanup.py`：新增正则规则匹配 `• tool_name(...)` 格式并剥离
- `group_nudge.md`：prompt 禁止条款扩展覆盖项目符号格式
- 测试通过：伪造格式被正确清理

## 备注

Retriever 提出的 Phase 2（engine 启动时随机 salt）属于过度工程，当前方案已足够。零宽字符 + 正则兜底是确定性防御，不需要对抗性升级。
