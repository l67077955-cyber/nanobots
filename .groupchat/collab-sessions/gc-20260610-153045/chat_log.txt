[Kirk]: 代码已读完，问题定位清楚了。当前压缩算法有 **5个结构性问题**：

---

## 1. 配置自相矛盾 — 压缩触发时中间区为空

你的当前配置：
- `max_messages: 30`
- `compress_ratio: 0.7` → 触发阈值 = `int(30 × 0.7)` = **21条**
- `compression_keep_recent: 18` → 保护尾部 **18条**
- `keep_user_messages: true` → 保护**所有**用户消息

当消息数达到21触发压缩时：tail占18条 + head（system prompt + 所有user消息），**可压缩中间区 ≈ 0~2条**。压缩形同虚设。

**修复**：`compression_keep_recent` 应远小于 `max_messages × compress_ratio`。建议 `keep_recent: 6`，或提高 `max_messages` 到 50+。

---

## 2. Broadcast cycle 内无压缩 — messages 局部变量无界增长

`broadcast.py` 中 `messages = engine._build_agent_prompt(...)` 构建一次后，cycle 内只 append 不裁剪。`maybe_compress` 只在 round 结束时调用（`run_loop.py:170`）。

结果：一个 round 内 agent 多轮工具调用，messages 可膨胀到数千条，直到 round 结束才压缩。这是之前 Kirk 重复循环事件的根因之一。

**修复**：cycle 每轮开始时裁剪 messages（保留 system prefix + 最近 N 条），或引入 cycle 级压缩回调。

---

## 3. `add_message` 即时裁剪 vs `maybe_compress` AI摘要 — 互相打架

`add_message`（context.py:94-154）每次追加消息都做 message-count + char-budget 裁剪（**直接丢弃**）。`maybe_compress`（context.py:156-265）做 AI 摘要（**保留语义**）。

但 `add_message` 在每条消息写入时立即执行，`maybe_compress` 只在 round 结束时执行。**消息被 add_message 丢弃后，maybe_compress 再也看不到它们**，无法做有意义的摘要。

**修复**：`add_message` 应只做硬上限截断（安全阀），不做常规裁剪。常规压缩统一由 `maybe_compress` 处理。

---

## 4. 摘要 prompt 硬编码 500字 vs 配置 2000 tokens

`context.py:226` 写死 `"摘要不超过 500 字"`，但 `compress_max_summary_tokens: 2000`。500中文字 ≈ 750 tokens，2000 tokens 预算浪费。且硬编码无法通过配置调整摘要长度。

**修复**：prompt 中的字数限制应从 `compress_max_summary_tokens` 换算，或新增 `compress_max_summary_chars` 配置项。

---

## 5. Head 保护策略过于保守

`keep_user_messages=True` 保护**所有**用户消息。长对话中用户消息可能占 30%+，大幅压缩可用空间。且用户早期消息（如"帮我查X"）在压缩后价值远低于近期消息，不应与 system prompt 同级保护。

**修复**：改为只保护最近 K 条用户消息（如最近3条），早期用户消息纳入可压缩中间区。

---

**最严重是 #1 和 #2**：#1 让压缩几乎不生效，#2 让 broadcast 模式有内存爆炸风险。要修哪个？

## 历史压缩算法问题分析

我通读了整个压缩系统的核心代码（`context.py`、`message_converter.py`、`history_settings.py`、`visibility.py`、`context_validator.py`），发现以下问题：

---

### 🔴 严重问题

**1. `add_message` 字符预算裁剪：贪心 break 丢弃可容纳的消息**

`context.py:136-141`：
```python
for m in reversed(self.messages):
    if id(m) in head_id_set:
        continue
    c = len(m.get("content", ""))
    if available - c < 0:
        break  # ← 一条放不下就直接停，后面更小的消息全丢
    tail.insert(0, m)
    available -= c
```
从尾部往前遍历，遇到一条放不下的消息就 `break`，不再尝试更早的更小消息。假设尾部第3条消息有5000字放不下，但第4条只有200字完全放得下——它也被丢弃了。

**2. `add_message` 不尝试 `age_tool_log` 就直接丢弃**

`history_to_messages` 在放不下时会先尝试 `age_tool_log` 压缩工具日志再决定是否丢弃（第150-156行），但 `add_message` 完全没有这步。同一段代码逻辑，两处实现不一致，`add_message` 白白丢失可压缩的信息。

**3. `_TOOL_LOG_RE` 正则 `re.DOTALL` 导致跨行匹配**

`message_converter.py:15-20`：
```python
_TOOL_LOG_RE = re.compile(
    r"(• \w+\([^)]*\) → )"
    r"(.*?)"           # ← DOTALL下.匹配换行符
    r"(\(\d[\d,]*字\))",
    re.DOTALL,
)
```
`(.*?)` 在 `re.DOTALL` 模式下 `.` 匹配换行符，导致"预览文本"可以跨越多行，从一个工具调用的预览吞到另一个工具调用的字数标记。注释写的是"greedy within line"但实际不是行内匹配。

**4. `maybe_compress` 就地修改原始消息对象**

`context.py:211-215`：
```python
for msg in to_compress:
    original = msg["content"]
    aged = age_tool_log(original)
    if aged != original:
        msg["content"] = aged  # ← 直接修改 self.messages 中的对象
```
`to_compress` 中的 `msg` 是 `self.messages` 的引用，不是副本。如果 AI 摘要失败回退到 drop，或者中途异常，原始消息已被不可逆地修改。应该先做深拷贝或仅在确认替换后修改。

---

### 🟡 中等问题

**5. `history_to_messages` 保留所有 user/system 消息为 critical**

`message_converter.py:133-136`：
```python
for i, m in enumerate(msgs_full):
    if m["role"] in ("user", "system") or i == 0:
        critical.append(m)
```
所有 user 和 system 消息都被标记为 critical 不参与裁剪。在长对话中，用户消息可能占大量字符，直接耗尽预算，导致 assistant 回复全被裁掉——上下文变成只有用户自言自语。

**6. `add_message` 的 head+tail 重建在 `keep_all_users=True` 时破坏时序**

`context.py:146-152`：当 `keep_all_users=True`，head 包含所有分散在对话中的用户消息。重建时 `head_msgs + tail` 把所有用户消息提到最前面，破坏了对话的交替时序。

**7. `history_to_messages` 未计入省略提示的字符**

`message_converter.py:178-182`：插入了 `"[...earlier messages omitted...]"` 但没有从 budget 中扣除其字符数。虽然这条消息很短，但严格来说是预算计算的不一致。

---

### 🟢 配置/设计问题

**8. 当前配置下压缩几乎无意义**

用户配置：`max_messages=30`, `compress_ratio=0.7`, `compression_keep_recent=18`
- 压缩触发阈值：30 × 0.7 = 21 条消息
- 保护尾部：18 条
- 保护头部：至少2条（系统+首个用户），`keep_all_users=True` 时更多
- 可压缩中间区：21 - 18 - 2 = **最多1条**

压缩触发时几乎没有中间内容可压缩，AI 摘要调用形同虚设。

**9. `maybe_compress` 无异步锁**

`maybe_compress` 是 `async` 方法，直接修改 `self.messages`，但没有加锁。如果 `add_message` 在压缩过程中被并发调用，可能导致消息列表损坏。

[Kirk]: ## 结论

历史压缩算法存在 **9个问题**，其中4个严重bug会导致信息丢失或数据损坏。

## 关键发现

### 🔴 严重（会导致信息丢失）
1. **`add_message` 贪心break** — 遇到一条放不下的消息就停止，后面更小的消息全丢
2. **`add_message` 不尝试 `age_tool_log`** — `history_to_messages` 有这步压缩逻辑但 `add_message` 没有，两处实现不一致
3. **`_TOOL_LOG_RE` 正则跨行匹配** — `re.DOTALL` 让 `(.*?)` 跨行吞到另一个工具调用的字数标记
4. **`maybe_compress` 就地修改原始消息** — AI摘要失败时原始消息已被不可逆修改

### 🟡 中等（影响上下文质量）
5. **所有 user/system 消息标记为 critical** — 长对话中用户消息耗尽预算，assistant回复全被裁掉
6. **`keep_all_users=True` 破坏时序** — 重建时把用户消息全提到最前面
7. **省略提示未计入字符预算**

### 🟢 配置问题
8. **当前配置压缩几乎无意义** — `max_messages=30, compress_ratio=0.7, compression_keep_recent=18` → 可压缩中间区最多1条
9. **`maybe_compress` 无异步锁** — 并发调用可能损坏消息列表

## 备注

问题1-4建议优先修复，尤其是问题4（就地修改）和问题3（正则跨行），这两个是确定性数据损坏。问题8建议调整配置：降低 `compression_keep_recent` 或提高 `max_messages`。
