[Kirk]: ## Skill 提示词编排逻辑

### 核心架构：static/dynamic 双阶段

整个 prompt 按 `prompt_manifest.json` 中定义的 `order` 排列，以 `history` 为分界线切为两段：

**Static 区块（history 之前）** — 跨轮次不变，KV cache 友好
- 只能用 stable 模板变量：`{{agent}}`, `{{members}}`, `{{tools}}`, `{{identity}}` 等
- 包含组件：main_prompt, hard_rules, tool_instructions, persona, broadcast_hint, **skills**, leader_prompt, instructions, memory 等

**Dynamic 区块（history 之后）** — 每轮重建
- 可用 stable + volatile 变量：`{{datetime}}`, `{{round}}`
- 包含组件：**skills_overview**, group_context, examples, group_nudge, coding_principle, 记忆补充 等

---

### Skills 的 static/dynamic 拆分

`loader.py` 的 `build_skills_section()` 返回 `(static_content, dynamic_content)` 元组：

**Static → `skills` 组件（order=7）**
- 仅 `always: true` 且 `type: static`（默认值）的 skill
- **compact 模式**：每个 skill 只输出一行 `description + read_file 指针`（~180 chars），不内联全文
- 总预算 5600 chars
- 当前 always-on：cron, debug, memory, settings

**Dynamic → `skills_overview` 组件（order=12）**
- `always: true` 且 `type: dynamic` 的 skill（compact 模式）
- 非 always-on skill 的摘要列表（预算 8000 chars）
- undocumented scripts 自动发现（`scripts/` 下的 .py/.sh）
- untracked scripts（无 SKILL.md 的独立脚本目录）

---

### Skill 发现优先级

```
workspace/skills/{name}/SKILL.md  →  builtin/skills/{name}/SKILL.md
```

- workspace 优先，同名 builtin 被覆盖
- `_disabled.` 前缀目录整体跳过
- 无 SKILL.md 但有 `scripts/*.py|*.sh` 的目录作为 docless skill 注册

---

### 数据流

```
SKILL.md frontmatter (always, type, description)
       ↓
SkillsLoader.build_skills_section()
       ↓
(static_content, dynamic_content)
       ↓
_build_skills_content()  → "skills" 组件 (static phase, order=7)
_build_skills_overview() → "skills_overview" 组件 (dynamic phase, order=12)
       ↓
build_agent_prompt() 按 order 遍历，history 处切分
       ↓
static 组件 → stable_tpl_vars 展开
dynamic 组件 → all_tpl_vars 展开（含 datetime/round）
```

---

### 配置体系

- `~/.nanobot/prompt_manifest.json` 是单一数据源（order, phase, visibility, editable_by, label）
- import 时 `_sync_from_manifest()` 同步到模块级常量
- visibility 控制：`"leader"` 仅注入 leader，`"all"` 注入所有人

**一句话总结**：static 区块放 always-on skill 的紧凑指针（cache 友好），dynamic 区块放按需 skill 摘要 + 自动发现的脚本（每轮更新），两者以 history 为界，volatile 变量只在 dynamic 侧可用。

[Harper]: **结论：单轨是，跨Agent不是。**

具体分析：

### 单次对话内：✅ 前缀最大化

`_sys_msg_count` 快照机制让 `messages[:_sys_msg_count]` 永不修改。static phase 的所有内容一旦在 agent 启动时固定，后续每轮 prefix 不变，KV cache 命中。

### 群聊跨Agent：❌ 不是前缀最大化

12 个 static 组件中，**仅 5 个是全局共享**（不同 Agent 完全一致）：

| 共享前缀 (5) | Agent特异前缀 (7) |
|---|---|
| hard_rules | **main_prompt** (每个agent人设不同) |
| tool_instructions | **persona** |
| user_context | **skills** (always-on技能集不同) |
| broadcast_hint | **memory** (每个agent记忆不同) |
| group_context | **output_efficiency** |
| | **instructions** |
| | **leader_prompt** (仅Leader有) |

**实际情况**：Harper 的 prefix ≈ 5800 chars，Kirk 的 prefix ≈ 4500 chars（约差 1300 chars）。每个 agent 的 prefix 不共享，cache 在系统级分段存储。

### 最核心矛盾

```
group_context 在 static (order=7)  ← 跨Agent相同
memory        在 static (order=8)  ← 每个Agent不同
```

如果把 `memory` 放到 dynamic phase（history 之后），所有 Agent 的静态前缀会共享一致的 `[main_prompt ~ group_context]`（order 0-7），前缀长度更统一，但代价是 memory 每次轮次要重建 → 增加了 dynamic 负载。

**设计选择权衡**：当前方案牺牲了跨Agent前缀共享，换来了每个Agent内部 memory 稳定在前缀中（memory 不随轮次变化，cache 友好）。

### 一句话

不是前缀最大化，而是 **per-agent 前缀稳定化**——每个Agent自己的前缀锁死不动，但彼此不共享。如果目标是跨Agent缓存共享（批处理场景），需要把 agent-specific 组件全部移到 dynamic，只留 5 个全局组件在前缀。
