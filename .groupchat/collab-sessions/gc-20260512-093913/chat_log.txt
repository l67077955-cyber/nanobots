## Root Cause Analysis

Kirk的整个 `~/.nanobot/agents/kirk/config.json` 遭受了**OmegaConf/DictConfig元数据泄露** —— 每一个标量值都被序列化成双元素数组形式：

```json
// 期望的正确格式
"temperature": 0.55

// 实际的损坏格式  
"temperature": [0.555, {"NANOBOT_ENV_VARS": "...一大堆敏感凭证..."}]
```

这导致所有读取该文件的代码都拿不到纯字典/纯数值。

### 对超参数的直接影响

在回调处理中 (`callbacks.py:L229`)：
```python
agent = self._groupchat_engine.registry.get(name, {})
agent_hp = agent.get("hyperparams") or {}   # ← registry是从config.json反序列化的
```

由于config.json里的每一层都是嵌套的 `[val, metaObj]` 结构，即使顶层有个 `"hyperparams"` key，它的值也不是普通dict而是带metadata包装的畸形对象，所以 `.get()` 要么拿到None要么拿到乱的结构 → fallback成空列表。

而且目前kirk的config里根本没有独立的per-agent超参section——只有顶层的全局超参也是同样畸形的格式。

### Fix路径

这不是前端UI能修的——得修底层序列化器。两个可能入口：
1. **YAML loader**把OmegaConf DictConfig当成plain dict dump出去了，没unwrap internals
2. **JSON encoder**遇到了特殊类型的tuple/list不知道怎么扁平化

要我深挖具体的serializer位置来patch吗？还是你先手动修复这份config.json恢复干净结构？

## 根本原因锁定

**备份文件和live文件都有相同的损坏签名**——这意味着早在restructure发生之前，config已经被某种OmegaConf序列化器毒化了。

### 具体断裂链条

1. **存储端**：备份文件中顶层 `"hyperparams"` 的值是一个 **LIST**（不是dict）：
   ```json
   // config.json.bak
   "hyperparams": [
     {"temperature": [0.35, {...env_vars...}], "top_p": [0.88, {...}]},  // index 0: actual params wrapped in [val,meta]
     {"NANOBOT_MAXTOKENS": "16384"}                                       // index 1+: orphan metadata
   ]
   ```

2. **加载端** (`agent_loader.py:116`)：
   ```python
   global_hyperparams = json.loads(defaults_file.read_text()).get("hyperparams", {})
   ```
   这里预期得到的是 `dict`，但实际上拿到了上面那个 **list**。

3. **下游消费** (`agent_loader.py:190`)：
   ```python
   hyperparams = acfg.get("hyperparams") or (dict(global_hyperparams) if global_hyperparams else None)
   ```
   由于 `global_hyperparams` 是个list而不是dict，后续赋值给每个agent的 `agent_data["hyperparams"]` 要么是None要么是非dict → registry中的值是空的。

4. **Telegram UI侧** (`callbacks.py:230`)：
   ```python
   agent_hp = agent.get("hyperparams") or {}  # → {} → show "(无参数)"
   ```

### 为什么其他agent可能有而Kirk没有

live版本做了restructure加了 `agents.defaults.hyperparams`，但这个新的层级下根本没设per-agent超参。老的顶层破损list还在那里但不被新版reader解析了。所以Kirk既吃不到老结构的脏数据，也没有新结构的干净数据 → 空列表。

### Fix方案

最快的方式：清理config.json中残留的老旧破损数据结构，并在正确的层级初始化干净的默认超参。要不要我现在动手修？或者你想先看一下是谁写的这个OmegaConf风格的序列化器防止复发？
