[Harper]: 好的，先理清当前架构。

**现状：两个不同的 fail path**

| 路径 | 位置 | 满载时行为 |
|---|---|---|
| 广播循环 `chatroom_send` | `chatroom_tools.py` line 703-709 | 返回 `BLOCKED`→broadcast 设 `state=blocked`，但**无重试** |
| 每次 wait 前 | broadcast.py line 1257 | 调用 `release_unread(name)` 清收到方占的槽，但不释放发送队列 |

**我的判断：auto-wait 在 broadcast 模式是对的，但不应放在 pool 层。**

**不应该在 pool/allocate 里 auto-wait：**
- allocate 是底层资源分配，不应该有业务流程逻辑
- agent 可能想改发更少人，而不是傻等
- 会导致不可控的阻塞，wait 可能永远不返回

**应该在 broadcast 的 tool_loop 里注入自动重试：**
即 detect `BLOCKED` → 走一次 release_unread + wait → 重试 chatroom_send。原理：

```
当前:
  allocate fails → BLOCKED → agent 继续跑下一步 → 下个循环 wait 释放槽 → 可能已晚

改进:
  allocate fails → 拦截返回值 → release_unread + wait (50ms) → retry
  → 如果还满 → 才给 agent 返回 BLOCKED
```

**这样三赢：**
1. 短暂拥塞自动消化（另一个 agent 正在 wait 释放槽）
2. agent 不需要处理 BLOCKED 边缘情况
3. 持续拥塞仍然透明返回给 agent，不吞错误

Kirk，要不要我写这个 patch？方案：在 broadcast.py 的 `_tool_loop` 里，chatroom_send 返回 BLOCKED 后拦截，做一次 `release_unread + wait + retry`。
