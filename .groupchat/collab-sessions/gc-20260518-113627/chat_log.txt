[Harper]: 用户说得对。不能只给 skills 打补丁，要从组件注册层做。

**当前隐式逻辑：** `order < history = stable vars only; order > history = all vars`
**问题：** 位置决定变量权限，语义不清晰，新动态组件必须手动插到 history 后面

**基础架构方案：**

组件 manifest 加 `phase` 字段：

```json
{
  "skills": {
    "order": 7,
    "phase": "stable",    // ← 新增
    "resolver": null
  },
  "skills_overview": {
    "order": 12,
    "phase": "volatile",  // ← 新增
    "resolver": "skills_overview_resolver"
  },
  "history": {
    "order": 11,
    "phase": "volatile",
    "resolver": "history_resolver"
  }
}
```

**规则：**
- `phase=stable` → 只展开 stable vars → 放在 history 前
- `phase=volatile` → 展开所有 vars → 放在 history 后
- `resolver` 字段真正启用：`phase=volatile` 的组件可注册代码生成器（不限于模板文件）
- 排序完全由 `order` 控制，`phase` 只决定变量作用域

**优势：**
1. 新动态组件只需注册 + 写 resolver，位置自动在 history 后置
2. 静态组件位置灵活，不依赖 history 前顺序可自由调整

[Kirk]: ## 结论

提示词组件已按 `static`/`dynamic` 大类区分，替代原来靠 `past_history` 隐式追踪的方式。提交 `2363adb`。

## 关键发现

**机制变更：**
- 新增 `_FALLBACK_PHASES` dict，19 个组件全部标注 `static` 或 `dynamic`
- `COMPONENT_PHASES` 从 manifest `phase` 字段同步，fallback 默认 `static`
- `build_agent_prompt` 用 `COMPONENT_PHASES.get(key) == "dynamic"` 决定模板变量展开范围

**分类结果：**

| Phase | 组件 | 模板变量 |
|-------|------|----------|
| **static** (11个) | main_prompt, hard_rules, tool_instructions, persona, broadcast_hint, user_context, output_efficiency, skills, leader_prompt, instructions, memory | stable only |
| **dynamic** (8个) | history, skills_overview, group_context, examples, group_nudge, 工程原则, coding_principle, 记忆补充 | stable + volatile |

**术语统一：** `stable`/`volatile`（模板变量）vs `static`/`dynamic`（组件 phase）— 两个不同概念，不再混用。

## 备注

- 新增组件只需在 manifest 加 `"phase": "static"` 或 `"dynamic"`，自动继承正确的变量展开策略
- `skills_overview`（上轮拆分）已正确归为 dynamic，在 history 后可用 `{{datetime}}` 等变量
