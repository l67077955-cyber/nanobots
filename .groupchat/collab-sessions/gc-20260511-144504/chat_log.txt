上下文压缩架构（双层设计）

🔷 层级一：跨轮压缩 — HistoryContext.maybe_compress()

位置: groupchat/history/context.py:146-250
触发器: engine.py:1137（下一轮开始前）、engine.py:951（其他时机）
作用对象: master 消息列表本身（破坏性操作）

┌─ Protected Head ─┬─ Compressible Middle ─┬─ Protected Tail ─┐
│ system prompt    │                       │                   │
│ initial setup    │   这里被压缩或丢弃     │ 最后6条消息       │
│ leader指令       │                       │                   │
└──────────────────┴───────────────────────┴───────────────────┘


两种策略（按优先级）：
1. AI 摘要（若 summarize_enabled=true）— 用指定模型生成 ≤500字中文摘要，插入为一条虚拟的系统消息标记 [早期对话摘要（压缩了 N 条中间消息）]
2. Fallback：直接丢掉中间区域

阈值: 仅当消息数 ≥ max_messages × compress_ratio(=0.7) 时才触发。例如 max=30，则在≥21条时激活。

🔶 层级二：轮内修剪 — tool_pruning.prune_messages()

位置: groupchat/history/tool_pruning.py:135-205
触发器: tool_loop.py:216-218 — tool loop 的第2次及以上迭代
作用对象: LLM入参副本（浅拷贝），不改动原始消息列表

对每条 tool result：
  长度 > max_chars(≈3000) ?
    ↓ yes
  位于倒数 keep_recent(≈3)个 assistant turn之外?
    ↓ yes
  替换成一行摘要："[exec] ran npm test → exit 0, 47 lines"


这样后续迭代不会带着巨大的 stdout/stderr payload。

🔵 整体流程图

一轮对话结束
    ↓
engine._maybe_compress_history()
    → HistoryContext.maybe_compress()
        → IF msg_count > threshold (=21)
            → AI摘要 OR Drop middle
    
下一轮的每一次 tool iteration (iteration ≥ 2)
    ↓
prune_messages(master_copy, ctx_window)
    → IF total_chars > soft_ratio×char_window (=30%)
        → 大体积旧 tool result → 一行摘要
        
LLM inference ← pruned copy
