[Harper]: **会用，但有条件。**

forget 的价值在于**批量清理"过程产物"**，而不是每条都清。

| 场景 | 用 forget？ | 原因 |
|------|------------|------|
| 搜索10条结果只留3条 | ✅ 用 | 批量删除很高效 |
| 中间调试调用 (ls/curl/config) | 看情况 | 可能要回头看 |
| 最终产出（代码/报告）前的噪音 | ✅ 用 | 净化最终结果 |
| 单次调用就1条 | ❌ 不值得 | 成本高于收益 |

**核心逻辑：**
- 上下文窗口是硬上限，超过阈值必须清
- 中间产物vs最终产物的区分很重要
- forget本身就是一次工具调用，成本+1，所以批量比逐条划算

**实际操作时会这样：**
```
批量搜索 → 批量forget不相关的结果 → 保留的继续用
```

不用的场景：单次工具调用、直接读取本地文件（内容轻量）。

[Harper]: 结合之前的测试，说说我的判断：

**价值：**

1. **上下文净化** — 大量搜索后，只留关键几条，输出给用户时更干净
2. **批量高效** — 一次 indices=[0,1,2,3,4,5,6] 删除7条，比逐条删划算
3. **区分过程vs结果** — 保留中间结果到确认成功，失败后批量清

**局限：**

1. **索引偏移坑** — 删了0之后，原本的1变成0，继续删容易搞错
2. **keywords形同虚设** — 匹配工具名不匹配内容，想清"不相关结果"还得数索引
3. **成本+1** — 每次forget本身是工具调用，小批量时不一定值得
4. **没有选择性保留** — 只能删，不能合并/排序，只能靠后续重新组织

**实际决策树：**

```
搜索结果 > 5条？
├── 是 → forget批量清噪音
└── 否 → 直接用，不折腾

中间调试 > 3次？
├── 是 → forget批量清
└── 否 → 保留，可能回头查
```

**核心观点：** forget是**上下文管理工具**，不是每步标配。搜索密集型任务用，大局已定时用，不确定时会回看的场景不用。
