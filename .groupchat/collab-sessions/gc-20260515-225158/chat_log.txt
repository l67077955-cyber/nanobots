代码问题（3个）

1. _CONV_KEEP_TURNS = 6 硬编码 — 主因
broadcast.py:1282 硬编码了 6 轮对话保留量（≈18条消息），且不可配置。history_settings.json 里 max_messages: 30 和 max_context_chars: 50000 设了上限，但这个硬编码值在每次 agent reactivation 时直接决定保留多少上下文，绕过了配置。

改为 3 可减少 ~50% prompt tokens，直接降低响应延迟。

2. 摘要注入位置破坏前缀缓存
tool_pruning.py:335 在 sys_msg_count 位置注入摘要 system 消息。DeepSeek 的 automatic 缓存依赖前缀匹配——注入新 system 消息改变了消息数组结构，导致缓存失效。每次 pruning 后必然 cache miss。

3. 无缓存感知的重试/降级机制
缓存 TTL 过期（30-60s）后没有重试逻辑，直接全量 prompt 发送。可以在 cache miss 时用更小的模型或截断上下文重试。

配置问题（1个）

history_settings.json 的 context_window_tokens: 20000 合理但实际经常被突破（日志中 30k+ token 调用占 45/209=22%）。max_messages: 30 和硬编码的 _CONV_KEEP_TURNS=6 存在冲突——配置说最多 30 条，但代码每次 pruning 后保留 18 条，加上 system messages 轻松超过 30。
