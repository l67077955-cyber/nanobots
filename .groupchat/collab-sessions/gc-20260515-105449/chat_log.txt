[Harper]: ## 分析：前缀为什么不逐步增加

用户问的"前缀"指 Anthropic prompt caching 的 cache prefix。代码中的 `_apply_cache_control` **只标记 system messages**，不标记 user/assistant 历史消息。

```
_apply_cache_control 逻辑 (litellm_provider.py:198-235):
- 4 个 breakpoint 配额，tools 占 1 个
- 剩余 3 个配额 → 只给最后 N 条 system messages
- ✅ system messages → cache_control: ephemeral
- ❌ user messages → 不加
- ❌ assistant messages → 不加
```

所以跨轮次时，**对话历史在不断增长**，但 system messages 是固定的（prompt builder 拼出来的那几条系统指令），因此 **cache prefix 不会变**。

这是 **有意为之的设计**：
- 如果每一轮都把前面所有 user/assistant 标记上 cache_control，那么 cache prefix 会随轮次无限增长 → 每轮都得刷新缓存，命中率反而低
- 现在的做法是 system prompt 被缓存、稳定命中；history 部分自然增长，不做 cache 标记

[Kirk]: ## 结论

前缀不会逐步增加是**刻意设计**，目的是利用服务端 **KV cache / prompt caching** 优化——前缀不变 → 缓存命中 → 跳过重复计算 → 省 token、省延迟。

## 关键发现

- **`_sys_msg_count` 快照**（`broadcast.py:685`）：agent 启动时记录系统提示词消息数，此后前缀 `messages[:_sys_msg_count]` 永不修改
- **裁剪只动尾部**（`tool_pruning.py:208-225`）：`prune_conversation_tail` 只裁剪对话历史（`messages[sys_msg_count:]`），保留最近 6 轮（`_CONV_KEEP_TURNS=6`）
- **变量分离**（`prompt_builder.py:652-672`）：stable 变量放前缀，volatile 变量（datetime/round）放末尾，确保前缀稳定
- **中断处理也不裁剪前缀**（`broadcast.py:1044-1047`）：注释明确说明"Keeping the full prefix intact guarantees prompt-cache hits"

## 备注

对话历史部分会随轮次增长，但被定期裁剪到固定窗口。前缀（系统提示词 + 工具定义 + 角色设定等）在 agent 生命周期内完全不变。
