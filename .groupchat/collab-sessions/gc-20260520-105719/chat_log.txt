[Harper]: ## Kirk 超时原因分析

从 `nanobot_stdout.log`（5月12日为主）和代码分析，Kirk 的超时分**3种类型**：

---

### ① wait() 等队友超时 — 最常见
Kirk 调用 `wait(from_agent="Harper", timeout=30/60)` 但 Harper 未在时限内回复。

日志证据（多条）：
```
11:39 → broadcast [Kirk] tool_result: wait (29c): ⏰ 等待超时 (60s)，未收到来自 Harper 的消息
19:03 → broadcast [Kirk] tool_result: wait (29c): ⏰ 等待超时 (30s)，未收到来自 Harper 的消息
22:44 → broadcast [Kirk] tool_result: wait (18c): ⏰ 等待超时 (60s)，未收到消息
```

**根因**：Kirk 先完成任务然后等 Harper，但 Harper 回复慢或被其他任务阻塞。

---

### ② LLM 调用超时 — broadcast 超时恢复机制触发
`broadcast.py` L850：LLM 调用超时（超时阈值 = `leader_call_timeout` 参数，默认 90s）

**处理流程**（代码 L857-922）：
1. 第一次超时 → 用 `no-tools, max_tokens=600, timeout=60s` 重试一次
2. 重试成功 → 继续正常循环
3. 重试也失败 → 注入占位消息 "⏳ [Kirk] 当前模型响应超时，我仍在线"，继续运行（不死）

**相关历史修复**（来自记忆宫殿）：
- **LLM 超时链修复**（5月11日）：长上下文时动态计算的 timeout 未传到底层 httpx，已打通传递链
- **broadcast error recovery 修复**（5月14日）：原超时 recovery 计数器只在 `timeout` 分支有限制，`error` 分支无限循环，已加 `MAX_CONSECUTIVE_ERRORS=3`

---

### ③ 外部服务超时 — Kirk 调第三方 API 超时
```
broadcast [Kirk] tool_result: exec (消息): 外网传输受阻（transfer.sh/uguu.se/catbox.moe 均连接超时）
```

**根因**：不是 Kirk 本身超时，而是他调用的外网文件传输服务连接不上。

---

### ④ 待命超时（AgentRunner standby）
队友全完成且 Leader 已发关停总结后，Kirk 进入待命模式 **120s**，等不到用户输入自动退出。

---

### 汇总

| 超时类型 | 根因 | 影响 |
|---|---|---|
| **wait() 等队友** | Harper 响应慢 → Kirk 干等 | 最常见，占多数 |
| **LLM 调用超时** | 模型响应超阈值(90s) | 有重试机制，重试失败后注入占位消息保活 |
| **外部服务超时** | 第三方 API/中转不可达 | Kirk 换方案或报告用户 |
| **待命超时** | 用户不输入超 120s | 正常退出行为 |

Kirk（nanobot agent）最近超时有 **3类原因**，当前最活跃的是 OpenRouter API 上游不稳定。

[Harper]: ## Kirk 超时原因分析

从 `nanobot_stdout.log`（5月12日为主）和代码分析，Kirk 的超时分**3种类型**：

---

### ① wait() 等队友超时 — 最常见
Kirk 调用 `wait(from_agent="Harper", timeout=30/60)` 但 Harper 未在时限内回复。

日志证据（多条）：

```
11:39 → broadcast [Kirk] tool_result: wait (29c): ⏰ 等待超时 (60s)，未收到来自 Harper 的消息

22:44 → broadcast [Kirk] tool_result: wait (18c): ⏰ 等待超时 (60s)，未收到消息
```

**根因**：Kirk 先完成任务然后等 Harper，但 Harper 回复慢或被其他任务阻塞。

---

### ② LLM 调用超时 — broadcast 超时恢复机制触发
`broadcast.py` L850：LLM 调用超时（超时阈值 = `leader_call_timeout` 参数，默认 90s）

**处理流程**（代码 L857-922）：
1. 第一次超时 → 用 `no-tools, max_tokens=600, timeout=60s` 重试一次
2. 重试成功 → 继续正常循环
3. 重试也失败 → 注入占位消息 "⏳ [Kirk] 当前模型响应超时，我仍在线"，继续运行（不死）

**相关历史修复**（来自记忆宫殿）：
- **LLM 超时链修复**（5月11日）：长上下文时动态计算的 timeout 未传到底层 httpx，已打通传递链
- **broadcast error recovery 修复**（5月14日）：原超时 recovery 计数器只在 `timeout` 分支有限制，`error` 分支无限循环，已加 `MAX_CONSECUTIVE_ERRORS=3`

---

### ③ 外部服务超时 — Kirk 调第三方 API 超时
```
broadcast [Kirk] tool_result: exec (消息): 外网传输受阻（transfer.sh/uguu.se/catbox.moe 均连接超时）
```

**根因**：不是 Kirk 本身超时，而是他调用的外网文件传输服务连接不上。

---

### ④ 待命超时（AgentRunner standby）
队友全完成且 Leader 已发关停总结后，Kirk 进入待命模式 **120s**，等不到用户输入自动退出。

---

### 汇总

| 超时类型 | 根因 | 影响 |
|---|---|---|
| **wait() 等队友** | Harper 响应慢 → Kirk 干等 | 最常见，占多数 |
| **LLM 调用超时** | 模型响应超阈值(90s) | 有重试机制，重试失败后注入占位消息保活 |
| **外部服务超时** | 第三方 API/中转不可达 | Kirk 换方案或报告用户 |
| **待命超时** | 用户不输入超 120s | 正常退出行为 |

## 现状分析：问题根因

当前 prompt 顺序（来自 `prompt_order.json`）：

```
[static 区 - 前缀可缓存]
  main_prompt, hard_rules, tool_instructions, persona, broadcast_hint, 
  user_context, output_efficiency, skills ← 静态skill内容
  leader_prompt, instructions, memory
[history] ← 变长，截断缓存前缀
[dynamic 区 - 每次不同，缓存无效]
  skills_overview, group_context, examples, group_nudge, 工程原则, coding_principle...
```

**核心问题：** `skills` 和 `skills_overview` 被拆成两个组件，且 `skills_overview` 放在 `history` 之后。历史记录每轮长度不同 → `skills_overview` 之后的整个前缀偏移 → 缓存命中率为零。

## 最优方案

**合并 `skills` + `skills_overview` 为一个组件，整体移到 history 之前：**

1. `_build_skills_content()` 合并静态+动态技能内容
2. 把 `{{datetime}}` 预渲染到内容里（反正 datetime 最后也会追加）
3. 删除 `skills_overview` 组件
4. 所有 skill 内容变成一个连续块，永远在 history 前面 → 前缀缓存命中

这是纯本地 JSON 配置 + 代码改动，不需要换 API/provider。
