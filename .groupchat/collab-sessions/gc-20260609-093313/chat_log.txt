## 当前上下文中打断逻辑的问题清单

### ✅ 正确的部分

`_can_interrupt` 的核心比较逻辑是正确的：
```python
s_rank = self._ranks.get(sender, 0)
t_rank = self._ranks.get(target, 0)
return s_rank > t_rank
```
rank 3 > rank 2 → True（能打断）✓，rank 2 > rank 3 → False（不能打断）✓

### 🐛 Bug 1：`wait()` 中 nudge 的参数顺序反了

**第622行**：
```python
if self._can_interrupt(agent_name, from_agent):
```

这里的语义是：`agent_name` 是调用 `wait()` 的人（等待者），`from_agent` 是被等待的忙碌者。`_can_interrupt(agent_name, from_agent)` 检查的是"等待者能否打断忙碌者"。

**但逻辑意图是反的！** 注释说"only nudge if caller has higher rank than target"——等待者（低等级）想催促忙碌者（高等级）回复，但低等级不应该能打断高等级。所以这个检查**恰好阻止了低等级催促高等级**，看起来是对的。

等等——再想一下场景：rank 2 的 agent 在 wait() 等待 rank 3 的 agent 回复。`_can_interrupt(rank2, rank3)` → `2 > 3` → False → 不 nudge。这意味着 rank 2 无法催促 rank 3 回复，**这是正确的行为**。

但反过来：rank 3 在 wait() 等待 rank 2 回复。`_can_interrupt(rank3, rank2)` → `3 > 2` → True → 会 nudge rank 2。**这也是正确的**——高等级催促低等级回复。

**结论：nudge 的参数顺序实际上是正确的。** 我之前的判断有误。

### 🐛 Bug 2：`interrupt_busy_agents` 中 "用户" 硬编码绕过

**第491行**：
```python
if sender != "用户" and not self._can_interrupt(sender, agent):
    continue
```

这意味着只要 `sender == "用户"`，就完全跳过等级检查，可以打断任何人。这是**有意设计**（用户消息最高优先级），但硬编码 `"用户"` 这个字符串是个脆弱点——如果用户名变了就失效。

### 🐛 Bug 3：`_try_interrupt` 的每轮中断计数上限与日志不一致

**第453行**：`if self._interrupt_counts.get(target, 0) >= 3:` — 限制为3次/轮
**第466行**：日志写 `count={}/1` — 日志说限制是1次/轮

**实际限制是3次，但日志暗示是1次。** 日志误导。

### 🐛 Bug 4（核心问题）：`interrupt_busy_agents` 重置了中断计数器

**第499行**：
```python
self._interrupt_counts[agent] = 0
```

`interrupt_busy_agents` 在打断后把 `_interrupt_counts` 重置为0。这意味着：
- 用户消息触发 `interrupt_busy_agents` → 重置所有计数器
- 之后的 `_try_interrupt` 又可以从0开始计数
- 这实际上让每轮中断限制形同虚设，因为用户消息会不断重置计数器

### 🐛 Bug 5：`send()` 中无条件调用 `_try_interrupt`

**第542/554行**：
```python
self._try_interrupt(name, sender)
```

每次 `send()` 都会尝试打断接收者。虽然 `_try_interrupt` 内部有等级检查，但**每次发消息都触发一次等级检查和日志记录**，即使等级不够也会写 debug 日志并设置 `_last_interrupt_sender`。这导致低等级 agent 每次发消息都会在 `_last_interrupt_sender` 中留下记录，可能干扰 UI 显示。

[Kirk]: ## 结论

当前上下文中打断逻辑存在 **5个问题**，其中1个是核心 Bug：

## 关键发现

| # | 问题 | 严重度 | 位置 |
|---|------|--------|------|
| 1 | `wait()` nudge 参数顺序 | ✅ 无bug | L622 |
| 2 | `"用户"` 硬编码绕过等级检查 | 中 | L491 |
| 3 | 中断计数限制是3但日志写 `/1` | 低 | L453 vs L466 |
| **4** | **`interrupt_busy_agents` 重置计数器使每轮中断限制形同虚设** | **高** | **L499** |
| 5 | `send()` 每次都写 `_last_interrupt_sender`，低等级也写 | 中 | L444/L542/L554 |

**Bug 4 是你说的"打断逻辑不太对"的根因**：`interrupt_busy_agents`（用户消息触发）在 L499 把 `_interrupt_counts` 重置为0，导致等级中断限制被绕过——低等级 agent 在用户消息之后可以反复打断高等级 agent，因为计数器已被清零。

**Bug 5** 也有影响：`_try_interrupt` 在等级检查**之前**就写了 `_last_interrupt_sender`（L444），低等级 agent 发消息也会覆盖高等级的中断来源记录，可能让 UI 显示错误的中断来源。

## 备注

- Bug 2 的 `"用户"` 硬编码建议改为检查 `sender == self._leader` 或引入一个特殊标记
- Bug 3 建议日志改为 `count={}/{limit}` 格式
