[Harper]: 看了完整 loader 逻辑，结论明确：**配置放在 SKILL.md 内部，不加单独配置文件**。理由：

## 当前架构是正确的

```yaml
# SKILL.md 顶部
---
name: cron
description: Schedule reminders...
always: true
type: static
homepage: https://...
metadata: {"nanobot":{"emoji":"⏰"}}
---
```

loader 直接从 frontmatter 读取元数据（`_get_skill_meta()`），不额外 I/O。没有"配置文件和状态的同步问题。

## 为什么不用单独配置文件

| 维度 | 单独配置 | 内嵌（当前） |
|------|---------|-------------|
| **原子性** | 复制 skill 要复制两个文件，可能丢配置 | 一个目录，全带走 |
| **编辑体验** | 改配置开两个文件 / 记两个路径 | 打开 SKILL.md，顶部就是 |
| **同步问题** | 修改 SKILL.md 可能忘记更新 config | 无同步问题 |
| **skill-creator 生成** | 要生成器多一个步骤 | 一步到位 |
| **loader 开销** | 多一次文件读取 + 解析 | 一次 frontmatter 解析完成 |
| **乱改风险** | 用户可能误删/格式错乱 | 一样有 frontmatter 风险 |
| **全局覆盖** | 覆盖** | 需要额外机制 | — |

唯一站得住脚的优势——**全局覆盖**，已经有解决方案：

1. `_disabled.skillname/` — 禁用一个 skill，零配置
2. 可以加一个 `workspace/config/skills-override.yaml`（如果将来有必要）覆盖 `always` 等字段，不污染 skill 本体

## 建议

**维持现状，内嵌 frontmatter。** 即可。** 如果将来需要全局控制逻辑（比如 "debug 降级为按需"），加一个可选的 `workspace/config/skills-override.yaml` 即可，优先级规则：

```
SKILL.md frontmatter ← skills-override.yaml ← loader 硬默认值
```

这样 skill 创作者保留默认值，平台运营方可以全局调整，各司其职。

[Kirk]: ## 结论

**推荐混合方案：SKILL.md 声明默认值 + config.json 覆盖。**

当前 `always` 放在每个 SKILL.md frontmatter 里，skill 自包含可移植，但用户无法轻量覆盖 builtin skill 的开关——必须复制整个文件到 workspace。在 `config.json` 的 `tools.skills.always_override` 加一层覆盖即可解决，`loader.py` 的 `get_always_skills()` 多一步 config 检查，改动极小。

## 关键发现

- `loader.py:391-399` — `get_always_skills()` 直接读 frontmatter，无覆盖机制
- `config.json` 的 `tools` 段目前无 skills 配置
- 用户关闭 builtin skill always-on 的唯一方式是复制整个 SKILL.md 到 workspace
- 12 个 skill 中 4 个 `always: true`（cron/debug/settings/memory），8 个 `always: false`

## 备注

- `type: static/dynamic` 也适合同样的覆盖模式
- 如果不想污染 config.json，也可以用 workspace 下的独立 `skills_config.json`
