## Bug #1 验证 —— CRITICAL: 压缩结果永不持久化

**结论：Bug confirmed.** `save_message()` 接收 `history` 参数但从不保存它。

证据链条：

1. **`context.py:L144`** — `add_message()` 最后一行：
   ```python
   self._state.save_message(sender, content, self.messages)
   ```
   传入了 `self.messages`（此时包含了修剪后的完整历史）。

2. **`persistence.py:L172-L177`** — `save_message()` 签名接受第三个参数 `history: list[dict]`，但函数体**完全不使用这个参数**：
   ```python
   def save_message(self, sender: str, content: str, history: list[dict[str, str]]) -> None:
       """Log a message to session chat_log.txt and session.jsonl."""
       if self._session_dir:
           with open(self._session_dir / "chat_log.txt", "a") as f:
               f.write(f"[{sender}]: {content}\n---\n")
       self.save_event("message", agent=sender, content=content)
   ```
   只写了单个消息到 `chat_log.txt` 和事件流，从未序列化完整 `self.messages`。

3. **`maybe_compress()` (L229/L244)** — AI压缩成功或fallback丢消息后都修改了 `self.messages`，但两个分支都没有调用任何形式的持久化。对比之下 `add_message(L144)` 每次都调用了。

4. **重启恢复能力为零** — 整个代码库没有任何地方能从磁盘重建 `self.messages`。没有 `load_messages()`、没有反序列化、没有replay逻辑。进程崩溃后重新启动时，HistoryContext初始化就是空的(`self.messages = []`, L44)。

所以这不是"压缩没持久化"这么简单——是整个会话历史的运行时内存副本根本没有备份机制。唯一留存的是逐条的append-only事件日志，而那是单向不可逆的。

---

## Bug #2 验证 —— MEDIUM-HIGH: add_message ↔ maybe_compress 竞态条件

两者之间完全没有锁保护。虽然目前Python协程的单线程特性降低了风险概率，但在以下场景仍可能出问题：

- `add_message()` 在第107行计算了 `head_indices`
- 如果在第107和第115行之间有另一个异步操作切换出去（虽然没有显式await，但如果未来加了IO就会出事）
- `maybe_compress()` 在同一时刻重写了整个 `.messages`

更现实的威胁：多次连续的AI压缩调用可能在同一个event loop tick中被调度两次（例如engine层的wrapper在不同位置被调用）。

## Bug #3 验证 —— LOW-MEDIUM: SummaryMsg可被二次压缩

`sender="系统"` (L223)。下一次触发压缩时：

- **Head保护**(L56-61)：只保护index=0和第一个sender为"User"/"user"/"用户"的消息
- **Tail保护**(L171-174)：固定保护倒数6条
- summary_msg既不属于head也不属于tail区间 → 落在中间的"可压缩区"，下次可能会再次被喂进AI或者直接被drop掉

这意味着经过几轮反复压缩，"关于之前的摘要的摘要"会出现信息衰减。

## Bug #4 （新增）—— HIGH: Char-Budget Trimming算法缺陷

**文件**: `context.py:L117-L342`

char-budget裁剪的逻辑是从尾部反向遍历收集消息直到budget用完(L126-133)，然后把head拼在前面。但是这里有一个严重的语义问题：

```python
tail: list[dict] = []
head_id_set = {id(m) for m in head_msgs}
for m in reversed(self.messages):
    if id(m) in head_id_set:
        continue
    c = len(m.get("content", ""))
    if available - c < 0:
        break      # ← BREAK而不是continue！
    tail.insert(0, m)
    available -= c
```

一旦遇到第一条超出剩余budget的消息就直接break停止处理后面的所有消息。这会导致大量较新的消息也被丢掉——即使它们单独来看很小。应该改成skip这条大的然后继续处理剩下的。

另外这里的dedup逻辑(L136-142)用`id(m)`来判重也很脆弱——如果两条字典对象的id相同但不是同一个对象会有误报；而且既然前面已经从原始列表中筛选过了不应该有重复才对。

## Bug #5 （新增）—— INFO: keep_recent=6硬编码未暴露为配置项

**文件**: `context.py:L171`
```python
keep_recent = 6
```
这是决定有多少条最近的尾巴不被压缩的唯一阈值。但它没有被纳入 `history_settings.json` schema中的任何一个section（包括已有的context_pruning下的keep_recent键名冲突）。如果要精细调节压缩粒度就必须改源代码。
