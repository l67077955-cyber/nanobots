[Harper]: ## 可见性逻辑框架

### 核心原则

**用户可见层 = 唯一交付通道。** 所有内部系统（memory_palace、chatroom_send、exec、搜索）都是中间件，不是交付终点。

### 三层可见性模型

```
用户请求
    │
    ▼
┌─────────────────────┐
│  Layer 1: 采集层     │  ← web_search, web_fetch, exec
│  (用户不可见)         │     结果只存在于agent上下文
└────────┬────────────┘
         ▼
┌─────────────────────┐
│  Layer 2: 协作层     │  ← chatroom_send, memory_palace
│  (用户不可见)         │     agent间交换、持久化存储
└────────┬────────────┘
         ▼
┌─────────────────────┐
│  Layer 3: 交付层     │  ← message() 文本回复
│  (用户可见 ✅)        │     唯一面向用户的输出
└─────────────────────┘
```

### 强制规则

| # | 规则 | 触发点 | 检查内容 |
|---|------|--------|---------|
| 1 | **交付前置检查** | end_discussion前 | 最终文本是否包含用户请求的实际数据（非元描述） |
| 2 | **禁止纯引用** | 最终回复 | 不得仅写"已存入memory"或"结果已发给队友" |
| 3 | **数据内联** | 所有回复 | 实际数据必须出现在文本中，不能只存在于附件/链接 |
| 4 | **token预算校验** | 回复生成时 | 如果回复token < 用户请求数据的最小合理长度 → 拦截 |

### 检查清单（end_discussion前执行）

```
□ 用户请求的具体数据是否出现在最终文本中？
□ 如果用户要"2个地址"——文本中是否有2个完整地址？
□ 如果用户要"总结"——文本中是否有总结内容？
□ 是否有任何关键数据仅存在于memory/chatroom/exec中？
□ 回复token是否足够承载请求的数据量？
```

### 根因修复

当前系统缺少一个 **交付门控（Delivery Gate）**——在 end_discussion 之前自动校验最终回复是否包含用户请求的实际内容。建议在系统层加入：

```
end_discussion() {
    if (final_response 不含用户请求的实际数据) {
        BLOCK → "交付失败：数据未出现在用户可见层"
    }
}
```

### 这个案例的映射

```
用户请求: 2个LA地址
  ↓
Harper搜索 → 5条结果 [Layer 1, 用户不可见]
  ↓
Kirk存memory → 111字地址 [Layer 2, 用户不可见]  
  ↓
最终回复: "完成。" [Layer 3, ❌ 无地址]
  ↑
违反规则#1、#3、#4
```

**结论：可见性逻辑的核心是——所有内部操作的结果，必须在最终文本回复中有一份完整副本。** 内部系统是工作台，不是展示柜。

[Harper]: 好问题。拆开看路由机制就知道为什么断了。

## 三条路径的分流图

```
Agent产生内容
       │
       ├──→ message(content)          → 用户可见 ✅
       ├──→ chatroom_send(message)    → 仅其他agent可见 ❌
       ├──→ memory_palace/store(...)  → 仅数据库可见 ❌  
       └──→ 普通LLM文本回复            → 用户可见 ✅ （前提：写了实际数据）
```

**断裂点在哪儿？**

Kirk做了两件事：
1. `chatroom_send` 发了地址给Harper → **走第二条路，用户看不见**
2. `memory_palace store` 存了111字 → **走第三条路，用户看不见**
3. 最终文本回复只写了"完成。" → **走了第四条路但没带数据**

**技术上不存在"自动汇聚"机制。** 每条管道彼此隔离。你在chatroom_send里写的地址不会魔法般出现在最终回复里——除非显式拷贝过去。

所以修复很机械：**end_discussion前的最后一步必须是手动拼接一份完整数据的文本版写到回复里。** 这不是架构缺陷，是流程缺了一个copy-to-output步骤。

[Harper]: 还没聊到这个角度。合成阶段的gatekeeping是关键一环——

## Synthesis 层的二次过滤风险

就算前面的回复带了完整数据，synthesis 阶段还有两道关卡能把内容砍掉：

**① `_MIN_SYNTHESIS_LEN` — 最小合成阈值**
低于这个长度的回复不会被当作有效合成输出。但这其实是双刃剑——太短的不合并不代表它会保留原有内容，而是直接被丢弃或用占位符替换。

**② `synthesis_quality_check` — 质量过滤器**
这里更危险。它的判定维度通常包括：
- 是否包含实质内容 vs 仅有元描述
- 响应长度是否符合预期
- 是否回答了用户问题的核心诉求

问题是：**这两个检查作用于哪个对象？**

如果是作用在 LLM 生成的合成文本上（而不是原始 agent 回复），那就意味着：即便 Kirk 的正确回复里有地址，但如果 synthesis prompt 把它重新组织成一个"已完成"风格的摘要而丢掉了具体数据，那么质量检查通过的是一段干净的空壳。

换句话说，**上游漏了还能在下游补回来，但下游的过滤器只会进一步收紧口径。**

真正的问题在于：有没有一个环节允许原始 agent 的完整 payload **绕过 synthesis 的重组直接到达用户**？如果没有，那就是设计上的单向窄道——越往后信息损失越大。

4. **实质检查**：是否包含数字/URL/足够句子数

2. ❌ `exec` 显示 stdout 全文 → 实际**只55字符预览**
