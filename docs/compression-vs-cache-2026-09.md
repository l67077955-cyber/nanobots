# 压缩 vs 缓存 vs 截断 —— C2 实证结论(2026-09-08)

> plan.md 批次 C2 第 4、5 项交付(C2.4 路线对照 + C2.5 结论文档)。
> C2 是**只测不改**批次:本文档不改任何代码、默认值或运维配置——决策与执行是批次 C3 的事。
> 三栏诚实分栏贯穿全文:**已证实**(不依赖价格假设)/ **估计**(方向可信、量级含假设)/ **证据不足**(明确写"不足",不猜)。

## 0. 一页结论

**已证实**(直接来自数据,不依赖价格假设):

1. 122 天 request_logs(2026-05-09 → 2026-09-08,64,095 条)归因出 **431 次压缩摘要调用**,全部靠 marker 启发式,**0 条** C0 真实字段(cost / cache_tokens 命中 / mode 标记)。〔A〕
2. Σ(C×(M−S)) = **+36,126,689 token**:压缩确实缩小了后续 prompt(token 计量为实测)。〔A〕
3. **5 次 S>M 膨胀事件**(摘要输出比被压中段还长,纯增 prompt 体积),其中 **4 次落在当前段 S12**。〔A〕
4. 受控实验(60 条视图 / 10 事实,同一事实集):摘要路线召回 = **(2+min(k,8))/10**,随摘要保留量 k 单调上升;确定性截断路线**恒 0.2**;k=0 时两路线相等,k≥1 时摘要严格占优。〔B〕
5. 截断路线 **0 次 LLM 调用**;摘要路线每次压缩 1 次调用(C1.2 后同批同中段视图共享)。〔B〕
6. **缓存维度两条路线无差别**:两者与原视图的最长公共消息前缀都只有 head 保护的 1 条——重写点同为第一个非保护消息。"换截断救缓存"不成立;缓存友好需要的是把重写点**后移**,不是换路线。〔D〕
7. governance:中段"系统"消息(话题公告/注入约束)压缩后可变为不可原文检索(暴露面已钉住);persona/hard_rules 每轮从 manifest 重建、结构性安全。〔C〕

**估计**(方向可信,量级依赖假设价格表/代理指标):

- 全窗口净收益:上界 **+$9.04**(节省按全价计)、下界 **−$0.75**(按缓存读价计)——**方向不定**。12 个分段中仅 5 段上下界同号可判:4 段稳健正(S3/S4/S5/S6,合计上界 +$5.15 / 下界 +$0.46),1 段稳健负(S8)。最大的段 S2(363 次)与当前段 S12 都是方向不定。〔A〕
- 摘要路线的显性成本:431 次调用合计 **1,247,059 token 输入 / 189,316 token 输出**(实测)≈ **$0.33**(假设价格表);缓存前缀失效损失 ≈ **$1.50**(cache_probe 代理 + 假设折扣 0.1)。〔A〕
- 生产摘要压缩比 S/M 平均 **15.2%**;受控曲线上这对应"摘要保留了约 2-3/8 的中段事实"区域——旁证一致,但生产的真实保留率 k 未测(见"证据不足")。〔A×B 交叉,非直接测量〕

**证据不足**(本文档明确不下结论;须等网关重启积累 C0 真实数据后重评):

1. 真实缓存命中率与压缩的因果效应(`usage.cache_tokens` 命中>0 的条目:0 条)。
2. 真实费用(`cost` 字段:0 条)与假设价格表的校准。
3. 生产摘要的真实事实保留率 k——召回曲线是受控扫描,不是生产点位。
4. **"若压缩真的频繁发生会怎样"的代表性**:当前本机 regime(30/0.7/20)在视图有界(C1.1 生效)后可压中段 ≈0-1 条,近乎 no-op;历史 431 次调用全部来自视图无界/旧配置时期。本报告的成本数字描述的是**历史**,不是当前配置下的未来。
5. 截断路线在生产环境的行为(零生产数据,仅受控实验)。

**对 C3 四选项的预判**(详见 §6,均为"数据支持什么/不支持什么",不代替决策):换路线救缓存——不支持(§0-6);仓库默认值——无数据支持改动;缓存友好改造与持久化——动机存在但量化未定,等 C0;本机 regime 近乎 no-op——事实清楚,修正方向是用户决策。

## 3. 路线对照(C2.4 核心)

对照对象:**摘要压缩**(HistoryContext 路线,`_compress_view`:head+摘要+tail 重建视图)vs **确定性截断**(tool_pruning 风格:丢最旧非保护消息,不调 LLM)。两条路线共享同一保护语义(首条+用户消息[可配]+尾部 keep_recent),差别只在"中段换成了什么"。

### 3.1 召回率(同一事实集)

| 摘要保留量 k(8 个中段事实中保留前 k 个) | 摘要路线召回 | 截断路线召回 |
|---|---|---|
| 0 | 0.2 | 0.2 |
| 1 | 0.3 | 0.2 |
| 2 | 0.4 | 0.2 |
| 3 | 0.5 | 0.2 |
| 8(全部) | 1.0 | 0.2 |
| ≥8 | 1.0 | 0.2 |

出处〔B〕:`TestRouteComparison::test_summary_vs_truncation_side_by_side`(k=0,1,3,8,12 参数化)+ `test_compress_all_dedup_preserves_recall_for_both_agents`(k=2)。附:keep_user_messages=True 时用户消息进 head 保护,keep=0 下限从 0.2 抬到 0.3——**保护策略与路线正交**。

结构性结论(不依赖生产 k 的取值):

- **k=0 时摘要 = 截断**(0.2 = 0.2):一条什么都没保留的摘要,召回上就是盲截断,还白付了一次调用。
- **k≥1 时摘要严格占优**,且优势 = k/10 单调。
- **截断的召回是常数**(保护下限),与中段内容、摘要器质量、模型版本全部无关——可预测、可文档化。
- **生产的 k 未知**:受控实验扫描的是结果空间,不是 nanobot 生产摘要器的落点(证据不足,见 §0)。他系统 92%→58% 只说明"生产 k 可以很低",不能当 nanobot 的数字。

### 3.2 下轮 prompt 足迹与成本

受控对照〔D〕(char 空间;原视图 1,257 char,中段 39 条共 847 char,`TestPromptFootprint`):

| k | 摘要大小 S(char) | S/M | 摘要路线节省 | 截断路线节省 | 摘要召回 | 截断召回 |
|---|---|---|---|---|---|---|
| 0 | 41 | 4.8% | 806(中段的 95%) | 847(100%) | 0.2 | 0.2 |
| 3 | 162 | 19% | 685(81%) | 847 | 0.5 | 0.2 |
| 8 | 358 | 42% | 489(58%) | 847 | 1.0 | 0.2 |

精确关系(测试钉为等式,非阈值):`节省(截断) − 节省(摘要) = 摘要消息自身的字符数`——摘要是**常驻税**:它换来召回,但每次后续调用都要重读。k 越大召回越高、税越重;保留全部 8 个事实时,摘要路线只省下截断的 58%。

生产 token 侧〔A〕(431 次事件实测):ΣM=1,247,059、ΣS=189,316,**S/M 平均 15.2%**,落在受控曲线 k≈2-3 区域(19%)——旁证一致, suggestive 而非结论。**由〔A〕数据推导(非分析器直接输出)**:截断路线在同一事件流上的每事件节省为 C×M 而非 C×(M−S),即比摘要路线多省 C×S(摘要被后续调用重读的部分);同时 5 次 S>M 事件上摘要路线的"节省"实为负(膨胀),截断无此失败态。

每事件成本结构:

| 成本项 | 摘要压缩 | 确定性截断 |
|---|---|---|
| LLM 调用 | 1 次/压缩(同批同中段共享,C1.2);431 次合计 1.25M in / 189k out ≈ $0.33〔A,估计〕 | **0**〔B/D〕 |
| 缓存前缀失效 | 有(重写点=第一个非保护消息)〔D〕 | **同样有**(同重写点)〔D〕 |
| 换回的输入缩减 | C×(M−S) | C×M(严格更大,差 = C×S)〔A 推导〕 |
| 中段召回 | (2+min(k,8))/10,生产 k 未知 | 恒 0.2〔B〕 |

### 3.3 缓存前缀发散(关键澄清)

〔D〕`TestPrefixDivergence`:压缩后视图/截断后视图与原视图的最长公共消息前缀**都恰好是 head 的 1 条**;两路线受保护区域(head+tail)字节级原样存活,差别只在中段替换物。因此:

- **缓存维度不能区分这两条路线**——截断把中段删掉同样让后续所有消息移位,前缀缓存从第一个非保护位起同样全断。"确定性"买到的是可预测性,不是缓存友好。
- 缓存友好的唯一杠杆是**重写点的位置**。仓库内已有先例:`tool_pruning.prune_conversation_tail_with_summary`(:305-325)刻意把摘要**追加进最后一条 system 消息**以保持条数稳定、护 DeepSeek 自动前缀缓存——这是 plan C3 选项 1 的原型。**其缓存收益同样未度量**(证据不足);本对照未对它做受控实验,它的"条数稳定=缓存友好"机制论断未经数据检验,列为 C3 若启动时的前置度量项。

### 3.4 失败模式对照

**摘要压缩(HistoryContext 路线)**:

1. **静默失忆**:召回损失 = k 的函数,k 不可观测、盲评不敏感(动机引他系统 92%→58%;nanobot 自身生产 k 未测)。〔B 结构性 + §1 动机〕
2. **governance decay**:中段系统约束可被摘要改写/丢弃(§5)。〔C〕
3. **缓存前缀作废**:每次压缩后下一轮历史前缀全冷。〔D + A 代理〕
4. **S>M 膨胀**:摘要比中段还长 → 负节省,无需价格假设即可判负;实测 5/431,4 次在当前段 S12。〔A〕
5. 摘要调用失败 → **fail-open 保留中段**(不丢数据,但该轮不缩;`context.py` "keeping N middle msgs uncompressed")。〔E〕

**确定性截断(tool_pruning 风格)**:

1. **确定性失忆**:中段全丢,召回=保护下限(受控 0.2)——损失可预测、可文档化、与模型无关。〔B〕
2. **约束零保留机会**:截断对中段系统消息是 100% 丢弃,连"提示词要求摘要保留"的缓解机会都没有(§5 有路线相关细节)。〔C 推论〕
3. **同样打断缓存前缀**(§3.3)。〔D〕
4. **无 LLM 依赖**:零费用、零失败态、零延迟。〔B/D〕
5. 无膨胀可能(不产生替代文本)。

两路线共有的真相:**中段信息只能靠保护策略存活**(head/tail/用户消息/系统消息保护),保护策略与路线选择正交——调保护集对两路线同样有效。

解读:

- **为什么上下界差距大**:压缩省掉的 token 在压缩前大部分本来就是缓存命中,只值缓存读价(≈1/10)。净收益的符号取决于"节省的 token 按什么价计"——这正是没有真实 cache_tokens 数据时无法判定的原因。
- **S8 稳健负的成因是摘要费不是缓存**:S/M 高达 28.6%、事件窗内后续调用少(中位 7 次),摘要成本压过节省。**修法是收紧摘要上限/阈值,不是换截断**(截断在该段同样断缓存,且召回更差)。
- **S2(最大段)与 S12(当前段)方向不定**,但方向相反的诱因不同:S2 缓存损失 $1.255 是下界转负主因(该段事件前 cacheable 前缀中位 ≈13k tok);S12 是摘要费 $0.125 相对节省偏高 + 4 次膨胀。
- **膨胀集中当前段**:S12 的 N 中位 14,而本机 `compress_max_summary_tokens=2000`——允许的摘要空间比典型中段还大,膨胀是配置纵容的。仓库默认 600 token 更匹配(600 token ≈ 25-30 条短消息的中段)。
- **代表性警告(必读)**:431 次调用全部发生在 2026-05-15 → 09-04;S12 的 23 次也在其中,但那是**网关尚未重启到 C1.1(视图无界)时期**——同样的 30/0.7/20 配置在视图有界后可压中段 ≈0-1 条。**本节全部数字描述"压缩频繁发生的历史",不能代表"若当前配置真的一直跑会怎样"**;反之 §3 的受控实验描述"压缩真的发生时"的结构行为。两者互补,合起来仍是三栏里的"估计/已证实",不是对未来的预测。

## 5. governance decay〔C〕

- **暴露面(已钉住)**:中段"系统"消息(唯一真实生产者:`run_loop.py:108` 的话题公告;以及任何注入约束)落在可压中段,存活完全取决于摘要是否保留。摘要器收到了约束全文(测试断言其出现在 prompt 里——丢失是摘要选择,不是路由 bug),但不保留的摘要使约束在 `view_for` 中不可原文检索;`view_for_raw`(日志投影)仍持有——**视图级上下文丢失,不是磁盘数据丢失**。
- **结构性安全(反回归钉住)**:persona/hard_rules 每轮从 agent registry / manifest 模板重建,从不经 `add_message` 进历史——压缩在原理上无法衰减它们。
- **已落地缓解(选项 A)**:摘要提示词加"约束/规则/禁令类语句逐字保留,不得改写或省略"(commit `00a48a96e`);合规摘要保留的约束可证明逐字存活(摘要原样插入视图,无后处理丢弃)。
- **诚实局限**:提示词不是强制——不服从的摘要器的暴露面测试**故意仍然通过**;防护强度 = 模型服从性,未度量。
- **选项 B(全系统消息入 head 保护)被否的决定性理由**:压缩摘要自身 sender=系统,入保护则每轮摘要永久堆积、压缩自毁。
- **路线相关细节(给 C3 的推论)**:上述否决理由是摘要路线特有的——纯截断路线不产生系统消息,把系统消息纳入保护集不会自毁(代价是系统消息永久留存挤占视图)。若 C3 真考虑换截断,选项 B 需重新评估,不能沿用本否决。

## 6. 建议(对应 plan C3 四选项;本文档不改任何代码/默认值)

### 6.1 缓存友好压缩改造(摘要追加进最后一条受保护消息,重写点后移)

- **数据支持**:〔D〕现行两路线都在第一个非保护位断前缀——想救缓存只能动重写点,这正是本选项;〔A〕全窗缓存损失估计 $1.50(占全价节省 14%),S2 的下界转负主因就是缓存($1.255)。
- **数据不支持**:没有任何一段的**稳健**负收益由缓存主导(S8 稳健负是摘要费问题);tool_pruning 先例的缓存收益同样未度量,"条数稳定=缓存友好"未经检验。
- **证据不足**:真实缓存命中 0 条 → 缓存损失的全部 $ 数字是代理估计。
- **判定:暂缓,等 C0**。重启后若 analyzer 显示压缩事件后 `usage.cache_tokens` 命中率显著下降、且净下界被缓存损失翻负,再做;做之前先给 tool_pruning 先例补一个受控前缀发散实验(§3.3 的方法直接可用)。

### 6.2 阈值/路线调整(上调阈值;或对自动前缀缓存 provider 走截断)

- **数据不支持换路线**:〔B〕截断召回恒 0.2,摘要 k≥1 即严格占优;〔D〕截断不救缓存;〔C〕截断对中段约束零保留机会。截断仅在"k=0 的失忆摘要"场景下与摘要召回持平——那时的问题是要修摘要质量,不是换路线。
- **数据部分支持调参数**:〔A〕5 次 S>M 膨胀(4 次当前段),N≈14 配 2000 token 上限是配置纵容;摘要上限应与触发阈值下的预期中段体量匹配。
- **证据不足**:仓库默认值(200/0.8/20/600)本身无本机数据支持或反对——本机从未在仓库默认 regime 下积累可归因数据(分段标签全是"疑似");生产 k 未知。
- **判定:仓库默认值不动**;若 C0 后确认 S/M 高企/膨胀持续,先收紧 `compress_max_summary_tokens` 再谈其他。

### 6.3 视图/压缩态持久化(W4,重启不丢压缩态)

- **数据支持**:无——分析器没有度量"重启后首轮重压缩"的重复成本。
- **证据不足**:〔A〕gateway.log 与 request_logs 的 48 天不一致无法区分实验进程/未落日志调用(见附录 A);重启后重压缩成本需要 C0 元数据 + 重启时间线才能归因。
- **判定:证据不足,等 C0**。重启后若 analyzer 显示重启后短窗内 `mode=history_compress` 调用成簇,重评。

### 6.4 本机 regime 修正(30/0.7/20;运维动作,非代码改动)

- **数据支持**:"近乎 no-op"是数据事实——阈值 21、尾保护 20、视图有界后可压中段 ≈0-1 条〔A 当前 regime 栏 + E〕;同时配 2000 token 摘要上限,与 ≈0-1 条的中段完全失配;S12(视图无界期)23 次中 4 次膨胀。
- **数据不支持的**:修正方向。两个方向都合理:(a) 若"基本不压"是有意的——显式关掉(`history_summarize_enabled=false` 或阈值调到永不触发),省掉每轮触发检查与偶发小压缩;(b) 若要它真干活——阈值需显著高于尾保护(如 max_messages≥60),并配匹配的摘要上限。数据无法替用户选,且任何修改都切换 regime,改后必须重新积累数据。
- **判定:事实清楚,方向待用户决策**;执行属 C3。

## 附录 A:启发式与置信度声明

1. **归因**:431 次摘要调用全部由 marker 启发式(`msg_count==1` + 摘要 prompt 标记"中期历史记录(共 N 条)",措辞自 2026-04-27 稳定)归因;另有 2,741 条"模型匹配+单消息"疑似条目因无 marker 被排除(宁可漏计不可误计)。C0 的 `mode=history_compress` 元数据重启后取代启发式。

3. **缓存**:pre-C0 无真实 cache_tokens,用两个代理——cache_probe 估计(字符/4)与压缩边界 prompt_tokens 跳降(混入同轮工具结果剪枝,高估压缩贡献);缓存折扣假设 0.1;"重写使整个可缓存前缀失效"是模型假设(与〔D〕的发散点观测一致)。

5. **gateway.log 污染(重要)**:分析时 gateway.log+轮转共 5,484 条 compressed 行,但与 request_logs 归因**重叠 0 天**;最大差异日 2026-09-08:gateway 4,950 行 vs request_logs 0 次。复查:当天全量测试后再数,仅 live 文件即 5,586 条且全部日期为 2026-09-08,期间 request_logs 零新增归因——这些行来自测试/实验进程(测试压缩走 loguru 进 gateway.log,假 provider 不落 request_logs;sink 由 `nanobot/cli/commands.py:323` 挂载)。**自 C2 批次日起,gateway.log 的 compressed 行数不可再当作生产压缩计数**;权威归因以 request_logs(重启后带 mode)为准。
